## 1. `eval()` 보안 안티패턴 제거

- **파일:** `ai_workspace/core/clustering/hdbscan_clusterer.py:92`
- **원인:** DB에서 읽은 임베딩 문자열을 파이썬 내장 `eval()`로 파싱하고 있었다. `eval()`은 임의 코드를 실행할 수 있어, 이 컬럼에 악의적인 문자열이 들어가는 경로가 생기면 RCE로 이어질 수 있는 보안 안티패턴이다. 같은 코드베이스의 `llm_client.py`는 이미 `ast.literal_eval`을 쓰고 있어 일관성도 없었다.
- **해결방법:** 파싱 로직을 `parse_embedding()` 모듈 함수로 분리하고 `eval()`을 `ast.literal_eval()`로 교체. 리터럴이 아닌 코드 실행 시도가 `ValueError`/`SyntaxError`로 명확히 거부됨을 테스트로 증명.
- **결과:** `tests/test_hdbscan_clusterer_parsing.py` 3개 테스트 통과 (정상 파싱 2건 + 코드실행 문자열 거부 1건). `grep eval(` 저장소 전체 결과 실제 호출부 0건 확인(매칭된 2건은 `route_after_cluster_eval`/`route_after_newsletter_eval` 함수명의 부분 문자열로 오탐).

## 2. `run_id`가 항상 0으로 고정되던 버그 수정

- **파일:** `ai_workspace/pipeline/stages.py:88-141`
- **원인:** `run_id`를 `int(logging.getLogger().name) if logging.getLogger().name.isdigit() else 0`으로 계산했는데, 루트 로거 이름은 항상 문자열 `'root'`이므로 이 값은 항상 0이었다(`'root'.isdigit()` → `False`). 이미 정상적으로 run_id를 채번하는 `db/batch_manager.create_new_batch()`가 구현되어 있었지만 호출되지 않는 죽은 코드였다. 모든 배치 실행에서 `news_letter.run_id`가 구분되지 않아 ML 실험 추적이 불가능했다.
- **해결방법:** `Stage5_NewsletterGeneration.execute()` 시작부에서 `create_new_batch(clusters)`를 호출해 `cluster_history` 테이블에 정식 run_id를 발급받고, 이 값을 모든 클러스터의 state에 동일하게 주입하도록 수정.
- **결과:** `tests/test_stage5_run_id.py`로 (1) `create_new_batch`가 실제 호출되는지, (2) 모든 클러스터 state의 `run_id`가 `create_new_batch`의 반환값(42)과 일치하는지, (3) 기존 버그의 전제(`'root'.isdigit()`)가 실제로 항상 False임을 mock 기반으로 검증. 2개 테스트 통과(수정 전 재현 테스트도 실제로 실패하는 것을 확인한 뒤 수정). 실제 DB 대상 통합 검증(`SELECT DISTINCT run_id FROM news_letter`)은 로컬 PostgreSQL 환경에서 별도 확인 필요(이 워크트리는 DB 없음).

## 3. DB 커넥션 풀 반환 오류 수정 (conn.close() → release_connection())

- **파일:** 9개 파일, 15곳 (`pipeline/stages.py:82`, `core/user_embedder.py:115`, `core/clustering/hdbscan_clusterer.py:123`, `crawler/rss_collector.py:78`, `crawler/embedding_generator.py:36,89,151`, `crawler/content_extractor/extractor.py:76,93`, `workflow/nodes.py:408`, `db/user_log_queries.py:270`, `db/schema.py:43,89,124,155`)
- **원인:** `get_connection()`으로 대여한 커넥션을 `release_connection()`(→ `pool.putconn()`) 대신 `conn.close()`로 반환하고 있었다. `psycopg2.pool.ThreadedConnectionPool`은 `close()`로 끝난 커넥션을 여전히 "대여 중(`_used`)"으로 추적하므로, 반복 실행 시 풀이 서서히 고갈되어 `PoolError`나 불필요한 direct-connection 폴백이 발생할 수 있다.
- **해결방법:** 9개 파일의 import를 `from db.connection import get_connection, release_connection`으로 확장하고, 15곳의 `conn.close()`를 `release_connection(conn)`으로 일괄 교체(sed 스크립트로 기계적 치환 후 각 라인 수동 검토).
- **결과:** `tests/test_no_raw_conn_close.py`로 저장소 전체 `grep conn.close()` 결과가 `db/connection.py`의 정상 폴백(release_connection() 내부의 putconn 실패 시 close) 1곳만 남았는지 자동 검증 (통과). 9개 파일 모두 `py_compile` 구문 검증 통과. 전체 pytest 스위트(6개 테스트) 회귀 없이 통과. DB가 없는 워크트리라 런타임(실제 커넥션 대여/반환) 검증은 로컬 PostgreSQL 환경에서 전체 파이프라인 실행 후 커넥션 풀 소진 여부 모니터링으로 별도 확인 필요.

## 4. 추천엔진 유저 히스토리 임베딩의 Temporal Data Leakage 수정

- **파일:** `ai_workspace/recommend_engine/src/data/data_loader.py:194-280` (신규 `compute_history_embedding` 추가 + `build_user_profiles` 리팩터링), `ai_workspace/recommend_engine/src/features/feature_engineer.py:14-31, 117-131`
- **원인:** `build_user_profiles()`가 `history_embedding`을 `datetime.now()` 기준 최근 28일 로그 전체로 **단 한 번** 계산해서 학습 데이터의 모든 row에 동일하게 사용했다. `hours_since_published`에는 row별 `ref_time` 보정이 있었지만, 가장 예측력이 높을 `history_cosine_similarity`에는 이 보정이 전혀 없어 이른 시점 학습 row가 미래 클릭까지 반영된 히스토리 벡터를 쓰고 있었다. 이는 오프라인 MRR/nDCG를 실제보다 낙관적으로 부풀리는 전형적인 data leakage다.
- **해결방법:** cutoff 시각 이전 로그만 사용해 히스토리 임베딩을 계산하는 `DataLoader.compute_history_embedding(user_id, cutoff_time, logs_df, news_dict)`를 추출하고, `FeatureEngineer.create_features()`가 학습 모드(`timestamps` 제공 시)에는 각 row의 `ref_time`을 cutoff으로 이 메서드를 호출하도록 수정. 실시간 추론 모드(`timestamps=None`)는 성능을 위해 기존처럼 `build_user_profiles()`가 미리 계산해둔 '현재 시점' 스냅샷을 그대로 재사용(추론 시점엔 어차피 cutoff=now이므로 동일한 값).
- **결과:** `tests/recommend_engine/test_history_embedding_leakage.py` 3개 테스트로 검증: (1) cutoff 이후 로그가 실제로 제외됨, (2) 로그가 없으면 zero vector, (3) 이른 시점 row에 대해 미래 클릭이 섞이지 않고 point-in-time 값만 사용됨을 확인 — 수정 전에는 코사인 유사도가 0.394(오염된 전역 프로필 사용)였으나 수정 후 0.99 이상(해당 시점에 유효한 클릭만 반영)으로 바뀜을 실제로 관찰. 전부 통과. 실제 학습 데이터 기준 MRR/nDCG 재측정은 로컬 DB 환경에서 `python main_lgbm.py --train` 실행 후 재평가 필요(이 워크트리는 DB 없음).

## 5. `LGBMRanker`를 실제 LambdaRank 랭킹 모델로 전환

- **파일:** `ai_workspace/recommend_engine/src/models/lgbm_ranker.py` (전체 재작성), `ai_workspace/recommend_engine/config/config.yaml:58-63`
- **원인:** 클래스명은 `LGBMRanker`였지만 `objective: 'binary'`, `metric: 'auc'`로 학습되어 실제로는 point-wise 이진 클릭확률 분류기였다. `set_group()`/`lambdarank` 등 LightGBM의 랭킹 학습 API를 전혀 쓰지 않아, "랭커"라는 이름 및 MRR/nDCG 평가지표와 실제 학습 방식이 불일치했다.
- **해결방법:** `objective`를 `lambdarank`, `metric`을 `ndcg`로 변경하고 `label_gain: [0,1]` 추가. `_build_groups()` 메서드로 학습/검증 데이터를 `user_id` 기준 정렬 후 그룹 크기 배열을 계산해 `lgb.Dataset(..., group=groups)`로 전달하도록 `train()`을 재작성. `config.yaml`의 `lightgbm.params`도 동일하게 갱신(`LGBMRanker(params=config[...])`가 `.update()`로 클래스 기본값을 덮어쓰므로 둘 다 바꿔야 실제 반영됨). `reranker.py`의 MMR 로직이 이미 후보군 내 min-max 정규화를 하고 있어 lambdarank의 unbounded score로 바꿔도 하위 호환됨을 사전 확인(코드 변경 없이 grep으로 검증).
- **결과:** `tests/recommend_engine/test_lgbm_ranker_lambdarank.py` 2개 테스트: (1) `_build_groups`가 user_id 기준 정렬 및 그룹 크기(3개 유저 × 4행 = [4,4,4])를 정확히 계산, (2) 기본 `objective`가 `lambdarank`로 설정된 상태에서 합성 데이터(10유저×6행)로 실제 `lgb.train()`이 에러 없이 완료되고 `predict()`가 올바른 shape의 score를 반환. 전부 통과. 실제 프로덕션 데이터 기준 MRR/nDCG 개선폭 측정은 로컬 DB 환경에서 재학습 후 별도 확인 필요.

## 16. Negative Sampling에 랜덤 시드 고정

- **파일:** `ai_workspace/recommend_engine/src/data/lgbm_dataset.py` (전체)
- **원인:** `LGBMDataset.create_train_dataset()`의 negative sampling이 전역 `random.choice(all_news_ids)`를 시드 고정 없이 사용했다. LightGBM 모델 자체(`random_state=42`)는 고정했지만, 학습 데이터 구성(어떤 negative가 뽑히는지)은 실행마다 달라져 "재현 가능한 실험"이라 보기 어려웠다.
- **해결방법:** negative sampling 루프를 순수 함수 `_sample_negatives(rng, all_news_ids, excluded_ids, neg_ratio)`로 분리하고, `LGBMDataset.__init__`이 `_init_rng(seed)`를 통해 시드 고정된 로컬 `random.Random` 인스턴스(`self._rng`)를 생성하도록 수정. seed를 명시하지 않으면 `config['lightgbm']['params']['random_state']`(기본 42, 모델 학습에 이미 쓰이는 값과 동일)를 재사용해 "모델도 데이터도 같은 시드로 재현 가능"하게 통일.
- **결과:** `tests/recommend_engine/test_negative_sampling_seed.py` 4개 테스트로 (1) 이미 클릭한 뉴스가 negative 샘플에서 실제로 제외되는지, (2) 같은 시드로 두 번 샘플링하면 완전히 동일한 결과가 나오는지(재현성 증명), (3) 다른 시드는 다른 결과를 내는지(시드가 실제로 영향을 미치는지 sanity check), (4) `LGBMDataset._init_rng`가 표준 `random.Random(seed)`와 동일한 시퀀스를 내는 로컬 인스턴스를 만드는지 검증. 전부 통과. 전체 pytest 스위트(40개) 회귀 없이 통과.

- **원인:** `db/connection.py`가 `config/settings.py`에 이미 존재하는 `Settings` 클래스(중앙 설정)를 쓰지 않고 `_initialize_pool()`과 `_create_direct_connection()` 두 곳에서 각각 독립적으로 `os.getenv("DB_HOST", ...)` 등을 호출하고 있었다. 기본값도 `"password"`로, `.env.example`의 예시값(`recsyspeople`)이나 `recommend_engine/config.yaml`의 값과 서로 달라 "이 프로젝트의 DB 접속 정보가 정확히 무엇인가"에 대한 단일 진실 공급원이 없었다.
- **해결방법:** `Settings`에 `DB_HOST`/`DB_PORT`/`DB_USER`/`DB_PASSWORD`/`DB_NAME` 필드를 추가(기본 비밀번호는 `"password"` 같은 그럴듯한 하드코딩 대신 빈 문자열로 바꿔, 설정 누락 시 조용히 잘못된 자격증명으로 연결 시도하지 않고 명확히 실패하도록 함). `db/connection.py`에 `_build_db_config()` 헬퍼를 추가해 두 커넥션 생성 경로(`_initialize_pool`, `_create_direct_connection`) 모두 이 함수 하나만 호출하도록 통합하고, 중복된 dict 리터럴을 제거.
- **결과:** `tests/test_db_connection_settings.py` 2개 테스트로 (1) `_build_db_config()`가 `os.getenv`가 아니라 `Settings` 속성값을 그대로 반영하는지(Settings를 patch해서 커스텀 값이 그대로 나오는지 확인), (2) `DatabasePool._initialize_pool()`이 실제로 `_build_db_config()`를 호출해 그 결과를 `ThreadedConnectionPool`에 전달하는지(psycopg2 mock, 실제 DB 연결 없이 검증) 확인. 전부 통과. 전체 pytest 스위트(54개) 회귀 없이 통과.

## 25. `recommend_engine`의 DB 자격증명을 환경변수 우선으로 통일 + 평문 비밀번호 제거

- **파일:** `ai_workspace/recommend_engine/src/data/data_loader.py`, `ai_workspace/recommend_engine/config/config.yaml:33-40`
- **원인:** `recommend_engine/config/config.yaml`에 DB 비밀번호(`"recsyspeople"`)가 평문으로 커밋되어 있었다. `DataLoader.__init__`도 이 YAML 값만 그대로 사용해, 상위 파이프라인(`ai_workspace/db/connection.py`, Task 24에서 `Settings`로 중앙화)이 쓰는 환경변수(`DB_HOST` 등)와 완전히 분리된 별도의 자격증명 소스였다. 같은 DB를 가리키면서도 두 서브 프로젝트가 설정을 공유하지 않는 구조였다.
- **해결방법:** `resolve_db_config(yaml_db_conf)` 함수를 추가해 `DB_HOST`/`DB_PORT`/`DB_USER`/`DB_PASSWORD`/`DB_NAME` 환경변수가 있으면 최우선으로 쓰고, 없을 때만 `config.yaml`의 `database` 섹션 값으로 폴백하도록 `DataLoader.__init__`을 수정(상위 파이프라인과 동일한 환경변수 이름을 공유해 `.env` 하나로 양쪽 다 설정 가능). `config.yaml`의 평문 비밀번호는 빈 문자열로 교체하고, 실제 값은 환경변수로 주입하라는 주석을 추가.
- **결과:** `tests/recommend_engine/test_db_config_env_precedence.py` 3개 테스트로 (1) 환경변수가 설정되어 있으면 YAML 값을 무시하고 환경변수를 쓰는지, (2) 환경변수가 없으면 YAML 값으로 정상 폴백하는지, (3) `config.yaml`을 실제로 파싱해 `database.password`가 더 이상 평문이 아닌 빈 문자열인지 검증. 전부 통과. 전체 pytest 스위트(57개) 회귀 없이 통과.

## 26. Embedder 중복(`NewsEmbedder` vs `BGEEmbedder`) 조사 — 통합하지 않기로 결정

- **파일:** `ai_workspace/core/embedder.py`(`NewsEmbedder`), `ai_workspace/recommend_engine/src/utils/embedder.py`(`BGEEmbedder`)
- **조사 배경:** 두 클래스 모두 BGE-M3(`BAAI/bge-m3`, 1024차원)를 로드하는 거의 동일한 보일러플레이트(디바이스 감지, `TOKENIZERS_PARALLELISM`/HF 로그 억제, `BGEM3FlagModel` 초기화)를 갖고 있어 리뷰에서 "중복"으로 지적됐다(`docs/adr/0002`, `recommend_engine/README.md`의 "알려진 한계"에 이미 기록). 실제 통합 가능 여부를 판단하기 위해 두 클래스의 공개 API와 호출부를 전수 조사했다.
- **조사 결과 (통합하지 않기로 한 근거):**
  1. **API가 실제로 다르다**: `NewsEmbedder`는 컨텍스트 매니저(`__enter__`/`__exit__`+`cleanup()`)로 설계되어 `with NewsEmbedder(...) as embedder:` 형태로 쓰이며 `generate_embeddings_batch(texts, batch_size)`를 제공한다. `BGEEmbedder`는 컨텍스트 매니저가 아니며 `encode_batch(...)`라는 다른 이름의 메서드를 제공하고, 빈 텍스트를 `None`으로 채워 리스트 정렬을 유지하는 등 세부 동작도 다르다. 단순 리네임이 아니라 호출부(양쪽 4개 파일)를 모두 고쳐야 하는 API 변경이다.
  2. **호출부가 완전히 분리되어 있다**: `NewsEmbedder`는 `pipeline/stages.py`, `core/reconstruction/repository.py`, `crawler/embedding_generator.py`, `workflow/nodes.py`(상위 파이프라인)에서만 쓰이고, `BGEEmbedder`는 `recommend_engine/scripts/generate_embeddings.py`(recsys 서브 프로젝트)에서만 쓰인다 — grep 결과 교차 참조 0건.
  3. **Task 21에서 두 서브 프로젝트를 독립 설치 단위로 공식화**했다. `recommend_engine`이 `core.embedder`를 import하려면 두 패키지 간 의존성을 새로 선언해야 하는데(현재는 서로 몰라도 되는 관계), 이는 "독립적으로 설치/배포 가능"이라는 Task 21의 목표와 충돌한다.
  4. **실제 동등성 검증이 이 환경에서 불가능하다**: BGE-M3는 수 GB 모델 다운로드 + 실제 GPU/CPU 추론이 필요해, DB도 없는 이 워크트리에서 "두 구현이 동일한 임베딩을 낸다"를 실측 검증할 방법이 없다. 검증 없이 팀원(성승우) 소유 코드의 공개 API를 바꾸는 것은 이번 세션의 위험 허용 범위를 벗어난다고 판단했다.
- **결정:** 지금은 병합하지 않는다. 대신 `recommend_engine/README.md`의 "알려진 한계" 섹션과 `docs/adr/0003`에 이미 문서화해뒀고, 필요하면 (a) 공통 보일러플레이트(디바이스 감지, 로깅 억제)만 아주 작은 공유 유틸로 뽑아내거나 (b) 실제 GPU 환경에서 두 구현의 출력이 동일함을 확인한 뒤 API를 통일하는 별도 계획으로 진행할 것을 권장한다.
- **결과:** 코드 변경 없음(의도적). 조사에 사용한 grep 근거는 이 항목에 그대로 남겨 향후 재검토 시 다시 조사하지 않아도 되게 함.
