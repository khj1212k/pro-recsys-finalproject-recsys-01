# 01. 팀 지표 누출 규명: 같은 모델, 추론 시점만 바꿨더니 MRR 0.8485 → 0.5636

| | |
|---|---|
| 데이터 | [team-synth] 팀이 남긴 LLM 페르소나 합성 클릭(100명, 뉴스레터 195건, 로그 19,500건). 평가 유저 31명 |
| 증거 등급 | `descriptive` (화이트박스 진단. 사전 등록한 가설 검정이 아니다) |
| 팀과 개인 | 추천 모델(LightGBM + MMR)은 팀원 성승우, 합성 데이터셋은 팀원 이선진의 작업이다. 이 글의 일은 팀이 끝난 뒤(2026-09-25부터) 단독 fork에서 그 결과물을 재현·검증한 것이다 |
| 한 줄 | 팀 평가 방식으로 추론하면 정답이 피처에 섞여 MRR이 +0.2849 [+0.1581, +0.4177] 올라간다. 누출을 걷어내면 모델은 인기도 베이스라인과 구분되지 않는다 |

## 문제

팀 최종 보고의 추천 성능은 MRR 0.897이었다. 팀 스스로 "과제가 너무 쉬운 것 아닌가" 의심했지만 원인은 규명되지 않은 채 프로젝트가 끝났다. 팀 DB는 이미 없고, 남은 것은 아카이브한 CSV와 npy, 그리고 세 시점의 코드였다. 0.897이 무엇을 재는 숫자인지, 평가 흐름의 어디가 그 값을 만드는지 알고 싶었다.

## 가설

팀 추론 코드는 사용자 히스토리 임베딩의 기준 시각을 "DB의 마지막 로그 시각"으로 잡는다. 그러면 시간순 80/20 분할의 검증 구간 클릭, 곧 채점할 정답이 히스토리 피처 안에 들어간다. 같은 학습된 모델에 추론 시점만 바꿔 적용하면 점수가 내려갈 것이다. 이 하나만 분리하면 누출의 크기를 잴 수 있다.

## 측정 설계

- **재현 하네스.** 팀 추천기의 실제 클래스를 세 git 스냅샷(`team-final` `ef7c176`, 자체 리뷰 중간 수정본 `a48cdff`, 현재 코드)에서 수정 없이 불러와 파일 아카이브 위에서 학습 → 추론 → 평가를 재생한다. 버전마다 서브프로세스로 격리하고, 데이터 sha256·버전별 `config.yaml` 해시·코드 내용 해시를 결과에 고정한다 ([`evaluation/recsys/team_repro/`](../../evaluation/recsys/team_repro/)).
- **두 추론.** 1차(point-in-time)는 로그를 고정 정답 구간 시작 시각 `2026-01-31T00:07:44` 이전으로 물리적으로 잘라낸 두 번째 로더로 피처를 다시 계산한다. 2차(as-written)는 같은 모델에 팀 방식(미제한 로그, 기준 시각 = 데이터셋 끝)을 쓴다. 정답 구간·학습 행·모델이 같으므로 추론 시점 누출 하나만 달라진다.
- **통계.** 시드 5개(fix-snapshot은 3개) × 평가 유저 31명, 시드를 쌍으로 재표본한 nested bootstrap 1,000회. 리포트의 결론 단어는 CI 부호에서 코드가 고른다.

## 결과

![코드 버전 3개에서 point-in-time과 as-written의 MRR, 쌍 차이와 95% CI](../assets/leakage_before_after_mrr.svg)

| 코드 | 시드 | MRR point-in-time [95% CI] | MRR as-written [95% CI] | 차이 [95% CI] |
|---|---|---|---|---|
| team-final | 5 | 0.5636 [0.4333, 0.7115] | 0.8485 [0.7328, 0.9418] | +0.2849 [+0.1581, +0.4177] |
| fix-snapshot | 3 | 0.5856 [0.4419, 0.7244] | 0.7937 [0.6598, 0.9024] | +0.2080 [+0.0978, +0.3350] |
| current | 5 | 0.6177 [0.4868, 0.7563] | 0.8033 [0.6829, 0.9109] | +0.1855 [+0.0865, +0.2957] |

살펴본 모델 설정 6개(objective, 조기 종료 방식, 고정 라운드) 모두에서 차이의 CI가 0 위다. 누출이 지표를 부풀린다는 결론은 설정에 기대지 않는다. 출처: [`team_repro_v2` 2-2절](../../reports/recsys/team_repro_v2.md).

누출을 걷어낸 뒤의 모델과 베이스라인 (point-in-time, 같은 정답·후보·구간, 모델은 current):

| 비교 | 결과 |
|---|---|
| 모델 − popularity, P@5 | −0.0645 [−0.1729, +0.0465], 구분 안 됨 |
| 모델 − popularity, MRR | +0.0977 [−0.0026, +0.2083], 구분 안 됨 |
| 모델 − onboarding cosine, MRR | +0.0193 [−0.1111, +0.1635], 구분 안 됨 |
| 모델 − random, MRR | +0.1456 [+0.0543, +0.2382], 모델 우위 |

popularity·onboarding cosine·cosine_history 중 어느 것에 대해서도 모델 우위의 CI가 없다. 그래서 내 첫 분석(v1)의 "모델이 베이스라인보다 낫다"는 결론을 철회했다. popularity의 점수는 정답 구간 이전 클릭이 없는 cold 유저에 몰려 있다(P@5 cold 0.7200, n=15 대 warm 0.2625, n=16). 이 데이터에서 점수를 올리는 것은 개인화보다 정답 밀도다.

**정정한 원인 추정.** 조기 종료가 트리 1개에서 멈추는 lambdarank 시드를 처음에는 "퇴화"로 보고 inner-valid 크기 같은 탓으로 추정했다. 틀린 추정이었다. LightGBM의 NDCG는 동점을 행 순서로 깨는데, 엔진의 학습 데이터 생성이 positive를 먼저 쌓아 검증 그룹의 첫 행이 항상 positive였다. 1라운드 검증 NDCG@5가 엔진 순서로 0.7370, 동점 무작위 기대값으로 0.6790, 역순으로 0.6225다. 검증 행을 섞자 best_iteration이 [35, 1, 1, 90, 1]에서 [35, 72, 49, 90, 28]이 되었다 ([`team_repro_v2` 0절 4번](../../reports/recsys/team_repro_v2.md)).

## 결정

1. **팀 코드를 고치지 않고 세 스냅샷을 그대로 재생했다.** 팀 코드가 틀렸다는 주장을 하려면 그 코드가 실제로 낸 값이어야 한다. 코드를 손보면 "내가 고친 모델의 값"이 된다. 대신 추론 시점 하나만 바꾸는 방식을 택해 변수를 하나로 줄였다.
2. **원인은 측정으로 확인한 것만 적고, 결론 단어는 CI 부호에서 코드가 고르게 했다.** 세 차례 방법론 검토 중에 두 가지가 드러났다. 리포트 v2는 사람이 문장을 먼저 쓰고 숫자만 채워서, 정의가 퇴화한 MRR 1.0을 "0.897에 근접"이라고 썼다. v2.1은 1라운드 종료의 원인을 추정으로 적었다가 틀렸다. 그래서 리포트의 판정 문장을 CI 부호에서 자동 생성하게 바꾸고, 확인하지 못한 원인은 "원인 미확인"으로 남기게 했다 ([ADR 0007](../adr/0007-recsys-offline-evaluation-protocol.md) 결정 9).
3. **합성 아카이브로는 정확도를 주장하지 않기로 했다.** 클릭이 LLM이 만든 라벨이라 어떤 절대값도 성능이 아니다. 정확도 주장은 공개 벤치마크에서만 하고, 이 데이터는 코드 결함이 지표를 움직이는 방향을 보는 진단에만 쓴다 (ADR 0007 결정 6). 다음 편의 EB-NeRD 평가가 이 결정에서 나왔다.

## 한계

- 클릭은 LLM 페르소나가 만든 라벨이고 세션이 약 6.3시간뿐이다. 평가 유저는 31명, 시드는 3~5개다. 20개가 넘는 구간을 병기하고 다중비교 보정을 하지 않았다. 개별 구간 하나로 "유의"를 말하지 않는다.
- **0.897은 재현하지도, 설명하지도 못했다.** 보고값은 값 하나만 기록되어 있고 측정 절차와 시점이 없으며, 103명/405건 스냅샷이 남아 있지 않다. 이 연구가 보인 것은 "추론 시점과 정답 창을 이렇게 잡으면 어떤 순위든 부풀려진다"까지다. 팀 평가 스크립트의 최근 6일 창은 이 아카이브(6.3시간)에서 학습 구간을 포함한 로그 전체를 덮고, 그 정의에서는 무작위 추천도 MRR 0.6523이다.
- 학습 쪽에도 정답 창 정보가 일부 남아 있다(negative sampler의 제외 집합). 따로 돌려 본 점검에서 효과는 검출되지 않았지만 그 수치는 이 리포트 실행에 포함되지 않는다.
- 코드 버전 간 누출 민감도 차이는 같은 조건 비교에서 검출되지 않았다. "team-final이 더 민감하다"고 쓰지 않는다.
- 팀은 절대 지표만 보고했다. FIX #4·#5는 팀이 아니라 팀 이후의 내 수정이므로 팀이 무엇을 잘못 귀속했다는 문장은 쓰지 않는다.
