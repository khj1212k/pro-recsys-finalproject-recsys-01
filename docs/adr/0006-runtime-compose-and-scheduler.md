# ADR 0006: 런타임 구성 - docker compose + supercronic, 임베딩은 Mac 호스트 MPS

## 상태
제안됨 (2026-09-26, 증거 수집 중 - 이 초안은 측정 전에 커밋한다)

## 컨텍스트
- 팀 시절 배치는 Airflow DAG이 `ai_workspace/main.py` 단계를 직접 불렀다. 배포 대상으로 잡은
  Oracle Always Free A1(arm64, 2 OCPU / 12GB)은 아직 확보하지 못했고, 당분간 모든 것이
  Apple M2 16GB 노트북 한 대(colima VM) 위에서 돈다.
- LLM 평가셋(클러스터 40개 층화 추출)을 만들려면 한국어 기사 5~7일치가 연속으로 쌓여야 한다.
  RSS는 피드마다 최근 20~50건만 보여 주므로(세계일보는 20건 ≈ 2.7시간 분량) 수집이 몇 시간만
  끊겨도 기사를 영구히 놓친다.
- 컨테이너(Linux VM) 안에서는 Apple GPU(MPS)를 쓸 수 없다. 2026-09-25 첫 수집에서 colima
  4 vCPU 컨테이너의 BGE-M3 CPU 임베딩은 모델 로드 174초, 355건의 첫 배치(8건)가 22분 안에
  끝나지 않았다(호스트가 다른 작업으로 과다구독된 상태라 깨끗한 수치는 아니다).
- 2026-09-26 호스트 MPS로 백로그 432건을 처리하던 중 파이썬 프로세스 메모리가 14GB까지 커져
  스왑이 가득 찼다. 원인: `NewsEmbedder`가 `max_length=8192`로 인코딩하고, 창 단위 길이 정렬로
  긴 기사 8건이 한 배치에 모이면서 eager attention의 (배치 x 헤드 x L x L) 점수 텐서가
  수 GB 단위가 됐다(transformers 4.38.2의 XLM-R은 SDPA가 아니라 eager attention).

## 검토한 대안 (스케줄러)
1. **Airflow standalone(프로필)** - 팀 시절 DAG을 그대로 살린다. 웹 UI·재시도·백필이 있지만
   api-server/scheduler/dag-processor/triggerer 프로세스가 상시 떠 있고 메타데이터 DB가 따로 필요하다.
2. **supercronic + `python -m jobs.run <job>`** - 컨테이너 하나에 crontab 한 장. 실행 기록은
   `job_runs` 테이블, 겹침 방지는 Postgres advisory lock, 실패 알림은 `jobs/notify.py`가 맡는다.
3. **호스트 cron/launchd만** - 가장 가볍지만 서버(Linux)와 Mac의 실행 경로가 갈라진다.

## 검토한 대안 (임베딩 실행 위치)
1. 컨테이너 CPU(서버와 같은 경로) 2. Mac 호스트 MPS(launchd) 3. ONNX/int8 양자화 CPU

## 사전 등록: 임베딩 입력 길이 상한(max_length) 결정 규칙
측정 전에 정한다. 측정 대상은 이 시점까지 수집된 본문 있는 기사 전부(`f"{title} {content}"[:8000]`,
수집 잡과 같은 텍스트), 토크나이저는 BAAI/bge-m3(특수 토큰 포함 길이).

- 후보 L ∈ {1024, 2048, 4096}. 기준선은 L=8192(현재 값, 8000자 절단 때문에 사실상 무절단).
- 조건 (a) 절단 비율: 토큰 길이 > L인 기사 비율 ≤ 2%.
- 조건 (b) 절단 영향: 잘리는 기사들에 대해 cos(emb_L, emb_8192)의 중앙값 ≥ 0.95.
  emb_8192는 배치 1, CPU(fp32)로 계산해 MPS 메모리 문제와 섞이지 않게 한다.
- 결정: (a)와 (b)를 모두 만족하는 가장 작은 L을 쓴다. 하나도 없으면 L=8192를 유지하고
  4096 토큰 초과 기사만 배치 1로 처리한다.
- 보조 보고(결정에 쓰지 않음): 잘린 기사의 top-5 이웃(전체 기사 emb_8192 기준) 보존율, 최소 코사인.
- 어떤 L이든 배치는 토큰 길이로 정렬해 묶고, 배치 크기 x (배치 내 최대 길이)^2 상한으로 메모리를 묶는다.
