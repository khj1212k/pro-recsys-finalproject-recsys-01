# ADR 0007: 추천 시스템 오프라인 평가 프로토콜

## 상태
채택됨 (2026-09-25)

## 컨텍스트
`evaluation/recsys/team_repro`는 팀이 아카이브해 둔 합성 데이터(`data/team_archive`, gitignored)
위에서 team-final(리포트 당시 코드) / fix-snapshot(중간 수정본) / current(이 브랜치)
세 코드 버전을 그대로 재현·비교하는 파일 기반 하네스다. v1 리포트
([`reports/recsys/team_repro_v1.md`](../../reports/recsys/team_repro_v1.md))가 나온 뒤
어드버서리얼 방법론 검토를 거쳤고, "unsound"(신뢰 불가) 판정을 받았다 - 핵심 원인은
추론 시점에 정답 구간의 클릭이 유저 히스토리 피처에 섞여 들어간 것(inference-time
leakage)이었다. 이 ADR은 그 검토에서 드러난 문제들을 근거로, 이 저장소의 추천
시스템 오프라인 평가가 앞으로 따라야 할 프로토콜을 결정한다 - team_repro 하네스뿐
아니라, 앞으로 recommend_engine 자체나 다른 평가 스크립트를 작성할 때도 이 결정을
따른다.

## 검토한 대안

### (A) 추론 기준 시각
1. **데이터셋 끝 시각(`pinned_now`)에 고정** (v1이 실제로 한 것, 그리고 `main_lgbm.py`의
   debug 모드 `inference_pipeline`이 실제로 하는 것 - `get_db_max_timestamp()`): 구현이
   가장 단순하고 팀의 실제 배포 동작과 일치하지만, 검증 구간의 로그가 존재하는 한
   히스토리 피처에 정답이 섞여 들어간다.
2. **고정된 point-in-time 경계(answer_start)** - 학습/검증 분할 경계 시각을 추론
   기준으로도 그대로 쓰고, 그 경계 이전으로 로그 자체를 물리적으로 잘라낸 뒤 그
   위에서 다시 피처를 계산한다.
3. **매 요청마다 실시간 "지금"** (실제 프로덕션의 온라인 서빙 시나리오) - 오프라인
   재현 실험에서는 흉내낼 방법이 없다(로그가 정적 스냅샷이므로).

### (B) 검증(정답) 구간 정의
1. 각 실행이 자기 학습 데이터의 80% 지점을 다시 계산 (v1) - negative sampling에
   따라 시드마다 행 수가 미세하게 달라져 정답 구간이 몇 초씩 드리프트한다.
2. **모든 arm/시드/버전이 공유하는 단일 고정 시각** - 클릭 로그(is_clicked==1)를
   시간순 정렬해 뒤 20%를 잘라내는 경계를 한 번만 계산해 재사용한다.

### (C) 베이스라인
1. 모델만 보고 상대적 개선을 주장 (v1이 baseline 표를 실었지만 모델 쪽에만 누출이
   있어 비교 자체가 불공정했다).
2. **모델과 완전히 동일한 로그/후보 풀/정답 구간으로 계산한 random·popularity·
   recency·category_match·cosine_history·onboarding_cosine 베이스라인을 필수로
   병기**하고, 모델이 이들을 넘지 못하면 "모델이 낫다"고 쓰지 않는다.

### (D) 모델 선택(조기 종료)용 검증 데이터
1. 정답 구간 자체를 조기 종료 검증셋으로 재사용 (v1, `main_lgbm.py` 원본 모두) -
   모델이 사실상 정답을 보고 트리 개수를 고른다. v1 재현에서 `best_iteration`이
   5개 시드 중 3개에서 1(사실상 학습 안 됨)이었다.
2. **학습 구간(정답 구간 이전) 자체를 다시 시간순으로 나눈 inner-validation**을
   조기 종료에만 쓴다.

### (E) 신뢰구간
1. 유저만 재표본하는 bootstrap (v1) - 시드 간 변동(학습 자체의 무작위성)이 구간에
   전혀 반영되지 않는다.
2. **시드 x 유저를 함께 재표본하는 nested bootstrap**, 시드 수(3~5개)와 유저 수를
   함께 명시.

### (F) 정확도 주장의 근거 데이터
1. 이 합성 아카이브(100 페르소나, LLM이 생성한 클릭)만으로 절대 성능을 주장한다 -
   클릭 라벨이 LLM 추론으로 만들어져 `category_match` 같은 명시적 신호와 순환성이
   있을 수 있고(v1 리포트 4절), 세션이 6시간16분뿐이라 신선도 피처가 사실상
   무의미하다.
2. **공개 벤치마크(EB-NeRD를 1차로, MIND를 보조로)에서 같은 파이프라인의 상대적
   효과가 재현되는지 확인한 뒤에야 정확도를 주장**하고, 이 합성 스냅샷은 화이트박스
   진단(코드 결함이 지표를 어느 방향/규모로 움직이는가)으로만 쓴다.

## 결정
1. **point-in-time 추론을 1차 프로토콜로 삼는다** ((A)-2). 피처/히스토리는 고정된
   `answer_start` 이전 로그에서만 계산하고, 이 로그 자체를 물리적으로 잘라낸 별도
   로더로 추론한다(단순히 "기준 시각" 인자만 바꾸는 것으로는 불충분하다 - team-final처럼
   cutoff 인식이 없는 코드에서는 로그 자체를 잘라야만 안전하다). 팀이 실제로 배포한
   흐름(추론 시각 = 데이터셋/DB의 마지막 로그 시각)은 "as-written(leaky)"이라고 명시한
   2차 행으로 남긴다 - 동일한 모델, 동일한 정답 구간으로 비교해 순수 추론 누출 효과만
   분리한다.
2. **정답 구간은 모든 arm/시드/버전이 공유하는 고정 시각 하나로 정의한다** ((B)-2).
3. **random/popularity/recency/cosine_history(+category_match, onboarding_cosine)
   베이스라인을 모델과 동일한 로그/후보 풀/정답 구간으로 병기하는 것을 필수로
   한다** ((C)-2). Cold/warm 유저를 나눠서, 그리고 이미 클릭한 아이템을 제거한
   변형으로도 함께 보고한다.
4. **조기 종료는 학습 구간 내부의 inner-validation만 쓴다** ((D)-2). `best_iteration`과
   distinct score 개수를 항상 기록한다.
5. **다중 시드 + nested bootstrap(시드 x 유저)을 기본으로 한다** ((E)-2). n(유저 수,
   시드 수)을 결과표에 항상 명시하고, 다중 비교 보정 여부를 밝힌다.
6. **정확도 주장은 공개 벤치마크에서만 한다** ((F)-2). EB-NeRD(1차, 이미
   `data/benchmarks/ebnerd`에 다운로드됨 - 라이선스상 이 Mac 밖으로 복사 금지)를
   기본으로, MIND를 보조로 검토한다. 이 저장소의 한국어 합성 스냅샷은 코드
   결함(누출, 그룹 정의, 후보 풀 규칙 등)의 상대적 효과를 값싸게 확인하는 진단
   도구로만 쓰고, 어떤 절대 지표도 "성능"으로 인용하지 않는다.
7. 각 코드 버전의 **`config.yaml`을 그대로 읽어** 쓰고(시간/출력 경로 등 평가
   재현에 필요한 필드만 덮어쓴다), 실제 쓰인 objective/config 해시를 결과에 기록한다
   (v1은 fix-snapshot을 실제 config(lambdarank)가 아니라 하드코딩된 binary로
   돌렸다).
8. 캐시 키에 **하네스+엔진 git SHA와 config 해시**를 포함해, 코드/설정이 바뀌면
   캐시가 자동으로 무효화되게 한다.

## 결과와 한계
**긍정적:**
- point-in-time 프로토콜은 team-final처럼 point-in-time cutoff 개념 자체가 없는
  코드에도 균일하게 적용 가능하다(로그 자체를 잘라내는 방식이라 엔진 코드 수정이
  필요 없다).
- 모델과 베이스라인을 정확히 같은 저울 위에 놓으므로, "모델이 낫다"는 주장이
  실제로 그 주장이 요구하는 증거(베이스라인 대비 우위)를 갖췄는지 항상 확인할 수
  있다.
- 캐시 키에 SHA/config 해시를 넣으면 코드를 고치고도 옛 결과를 모른 채 재사용하는
  사고를 원천적으로 막는다.

**한계:**
- 이 프로토콜은 데이터 누출·불공정 비교를 막지만, 클릭 라벨 자체의 품질(LLM 생성,
  순환성 가능성)은 고치지 못한다 - 그래서 공개 벤치마크 교차검증(결정 6)이 별도로
  필요하다.
- point-in-time으로 잘라낸 로그가 아주 짧으면(이 아카이브처럼 세션이 몇 시간뿐이면)
  '히스토리'가 사실상 비어 있는 cold 유저가 대다수가 될 수 있다 - 이건 프로토콜의
  결함이 아니라 데이터가 실제로 그렇다는 정직한 신호이며, cold/warm 유저를 나눠
  보고하는 이유이기도 하다.
- nested bootstrap도 여전히 n=수십 명 규모의 합성 유저에 대한 구간이라, 폭이
  넓고 다중 비교 보정 없이 여러 지표를 병기하면 개별 구간을 과신하기 쉽다 - 결과를
  읽을 때 n과 "다중 비교" 캐비엇을 항상 함께 봐야 한다.
- EB-NeRD/MIND 교차검증은 이 ADR이 결정만 했을 뿐 아직 실행되지 않았다 - 다음
  단계의 작업이다(`team_repro_v2.md` "다음 단계 시사점" 참고).
