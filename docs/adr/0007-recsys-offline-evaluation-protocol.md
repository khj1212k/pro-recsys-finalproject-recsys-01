# ADR 0007: 추천 시스템 오프라인 평가 프로토콜

## 상태
채택됨 (2026-09-25). 개정 (2026-09-26): team_repro v2 재검토를 반영해 증거를 실측 수치로 바꾸고, 시드 수·캐시·
조기 종료에 관한 과장을 고쳤다. 결정 4·5·7·8을 수정하고 결정 9·10을 추가했다. 개정 (2026-10-06): v2.1 재검토를
반영해 조기 종료가 1라운드에서 멈춘 원인을 지표의 동점 순서 아티팩트로 정정하고(대안 (D), 결정 4), 코드 버전 비교를
같은 조건끼리로 바꿨다(대안 (I), 결정 10). 원인 서술에 관한 규칙을 결정 9에 더했고 증거를 v2.2 수치로 바꿨다.
main 위로 옮기면서 (2026-10-06) 결정은 바꾸지 않았고, 증거에 '옮긴 뒤의 출처' 항목을, 한계에 재실행 대기 항목을 더했다.
상수 피처를 제거하는 정리 브랜치를 이 위에 쌓으면서 (2026-10-06) 증거에 '상수 피처 제거를 얹은 뒤의 출처' 항목을 더했다.

## 컨텍스트
`evaluation/recsys/team_repro`는 팀이 아카이브해 둔 합성 데이터(`data/team_archive`, gitignored) 위에서
team-final(팀 최종 코드) / fix-snapshot(자체 리뷰 중간 수정본) / current(이 브랜치) 세 코드 버전을 그대로
재실행·비교하는 파일 기반 하네스다. 추천 모델(LightGBM+MMR)은 팀원이 담당한 부분이고, 이 하네스와 평가는
그 모델을 재현·검증하는 작업이다.

v1 리포트([`reports/recsys/team_repro_v1.md`](../../reports/recsys/team_repro_v1.md))는 어드버서리얼 방법론
검토에서 "unsound" 판정을 받았다. 핵심 원인은 추론 시점에 정답 구간의 클릭이 유저 히스토리 피처에 섞여 들어간
것(inference-time leakage)이었다. v2는 재검토에서 "sound-with-caveats"를 받았지만 blocker 2건이 남았다.
(1) team-final-as-written 행이 노출 행 전체를 정답으로 세어 무작위도 MRR 1.0이 되는 정의 오류였는데 이를
팀 보고값 0.897(팀 최종 보고서에 값만 기재, 측정 절차·시점 미기록, 검증 불가)에 "근접"하다고 썼다. (2) 이력서 문장이
팀에 사실이 아닌 귀속을 했다. major 4건도 있었다. 조기 종료 모델이 여전히 트리 1개에서 멈췄고, 후보 풀 arm이 서로
다른 조건을 비교했고, 이 ADR 자체가 시드 수와 캐시 보장을 과장했다.

v2.1은 세 번째 검토에서 "sound-with-caveats"를 받았고 major 2건이 남았다. (1) 조기 종료가 트리 1개에서 멈추는
현상을 '퇴화'로 표시만 하고 원인을 작은 inner-valid·정답 밀도·learning_rate로 추정해 적었는데, 실제 원인은 조기 종료
지표의 동점 처리였다. (2) team-final과 current의 비교가 학습 길이가 다른 모델끼리였는데(한쪽은 트리 100개 이상,
다른 쪽은 5개 시드 중 3개가 트리 1개) 그 차이를 코드 버전의 성질로 읽었다.

이 ADR은 세 차례 검토에서 드러난 문제를 근거로, 이 저장소의 추천 시스템 오프라인 평가가 따라야 할 프로토콜을 정한다.
team_repro 하네스뿐 아니라 recommend_engine 자체나 다른 평가 스크립트에도 적용한다.

## 검토한 대안

### (A) 추론 기준 시각
1. **데이터셋 끝 시각(`pinned_now`)에 고정** (v1이 한 것, 그리고 `main_lgbm.py` 디버그 모드 `inference_pipeline`이
   하는 것 - `get_db_max_timestamp()`): 구현이 가장 단순하고 팀 배포 코드와 같지만, 검증 구간 로그가 있는 한
   히스토리 피처에 정답이 섞인다.
2. **고정된 point-in-time 경계(answer_start)** - 그 경계 이전으로 로그 자체를 물리적으로 잘라낸 뒤 피처를 다시
   계산한다.
3. **요청마다 실시간 "지금"** (온라인 서빙) - 정적 스냅샷 위의 오프라인 재현에서는 흉내낼 수 없다.

### (B) 검증(정답) 구간 정의
1. 각 실행이 자기 학습 데이터의 80% 지점을 다시 계산 (v1) - negative sampling에 따라 경계가 시드마다 몇 초씩 움직인다.
2. **모든 arm/시드/버전이 공유하는 단일 고정 시각** - 클릭 로그를 시간순 정렬해 뒤 20%를 자르는 경계를 한 번만 계산한다.

### (C) 베이스라인
1. 모델만 보고 상대적 개선을 주장 (v1은 베이스라인 표를 실었지만 모델 쪽에만 누출이 있어 비교가 불공정했다).
2. **모델과 같은 로그/후보 풀/정답 구간으로 계산한 random·popularity·recency·category_match·cosine_history·
   onboarding cosine 베이스라인을 필수로 병기**하고, 모델-베이스라인 쌍 CI로 판정한다.

### (D) 모델 선택(조기 종료)
1. 정답 구간을 조기 종료 검증셋으로 재사용 (v1, `main_lgbm.py` 원본) - 모델이 정답을 보고 트리 수를 고른다.
2. 학습 구간 자체를 시간순으로 나눈 inner-validation으로 조기 종료하되, 검증 행은 엔진이 만든 순서 그대로 (v2, v2.1) -
   1의 문제는 없어지지만 lambdarank(NDCG 조기 종료)가 여러 시드에서 1라운드에 멈춘다. LightGBM의 NDCG는 동점을 데이터
   행 순서로 깨는데(안정 정렬), 엔진의 `lgbm_dataset.create_train_dataset`이 positive를 그 negative들보다 먼저 쌓고
   이후의 시간순 분할과 그룹 정렬이 모두 안정 정렬이라 검증 그룹마다 positive가 첫 행이 된다. 동점이 많은 1라운드의
   NDCG가 부풀려져 이후 라운드가 그 값을 넘지 못한다. v2.1은 이것을 '퇴화'로 표시하고 원인을 추정으로 적었다.
3. **2에 더해, 검증 행을 고정 시드로 섞어 넘기고, 조기 종료 실행마다 동점 진단(1라운드와 선택된 라운드의 NDCG를 엔진
   순서·역순·동점 무작위 기대값으로)을 기록한다** (v2.2). 엔진 소스는 그대로 둔다 - inner-validation은 하네스가 만든다.
4. 동점에 영향받지 않는 사용자 정의 지표(동점 기대 NDCG)로 조기 종료 - 가장 깔끔하지만 엔진의 `LGBMRanker.train`이
   `feval`을 받지 않아 엔진 소스를 고치거나 `lgb.train`을 바꿔치기해야 한다. 재현 대상 코드를 바꾸지 않는다는 하네스
   원칙에 맞지 않아 조기 종료에는 쓰지 않고, 같은 지표를 진단용으로만 계산한다.
5. 최소 라운드나 learning_rate를 바꾸거나 고정 라운드로 학습 - 재현 대상(팀·자체 수정 코드의 설정)을 바꾸는 것이라
   1차 행에는 쓰지 않는다. 사전 선언한 고정 100라운드를 민감도 arm으로 둔다(inner-train만으로 학습, 검증셋 미사용).

### (E) 신뢰구간
1. 유저만 재표본하는 bootstrap (v1) - 시드 간 변동이 구간에 반영되지 않는다.
2. 시드 x 유저를 함께 재표본하는 nested bootstrap (v2) - 두 조건이 같은 학습 모델을 공유할 때도 시드를 따로
   재표본해 구간이 과하게 넓었다.
3. **2에 더해, 같은 모델을 공유하는 비교(추론 방식만 다른 누출 효과)는 시드를 쌍으로 재표본** (v2.1).

### (F) 정확도 주장의 근거 데이터
1. 이 합성 아카이브(100 페르소나, LLM이 만든 클릭)만으로 절대 성능을 주장한다 - 클릭 라벨이 `category_match` 같은
   명시적 신호와 순환성이 있을 수 있고, 세션이 6시간16분뿐이라 신선도 피처가 무의미하다.
2. **공개 벤치마크(EB-NeRD 1차, MIND 보조)에서 같은 파이프라인의 상대 효과가 재현되는지 확인한 뒤에만 정확도를
   주장**하고, 이 합성 스냅샷은 화이트박스 진단으로만 쓴다.

### (G) 리포트의 결론 문장
1. 결론 문장을 사람이 미리 써 두고 숫자만 채운다 (v2) - 숫자가 바뀌어도 문장이 그대로라 MRR 1.0을 "팀 보고값 0.897에 근접"이라고
   썼다.
2. **결론 단어를 CI 부호에서 자동으로 고른다** - `metrics.ci_verdict()`가 positive/negative/inconclusive를 돌려주고,
   리포트 생성기는 그 값으로만 "부풀린다/검출되지 않는다", "모델 우위/열위/구분 안 됨"을 고른다.

### (H) 실행 캐시 키
1. 하네스·엔진의 HEAD git SHA + config 해시 (v2) - 커밋 안 된 수정이 옛 SHA 키로 캐시됐다(v1 SHA 키 아래 v2 형식
   결과 10건). 데이터·answer_start·top_k도 키에 없었고, 코드 아카이브는 존재 여부만 확인했다.
2. **실제 실행되는 파일의 내용 해시 + 데이터 sha256 + answer_start/top_k/추첨 횟수/라운드 정책/검증 행 순서**,
   아카이브는 ref SHA가 바뀌면 다시 풀고, 감시 경로가 dirty면 최종 JSON을 쓰지 않는다.

### (I) 코드 버전 비교의 조건
1. 각 버전을 자기 config 그대로 비교 (v2.1) - team-final(binary·AUC 조기 종료)과 current(lambdarank·NDCG 조기 종료)는
   objective에 따라 조기 종료 지표와 멈추는 라운드가 달라, 두 모델의 차이에 코드·objective·학습 길이가 섞인다.
2. **같은 조건끼리 비교**: 둘 다 같은 objective와 같은 조기 종료 지표(current에 objective만 덮어씀), 그리고 둘 다 조기
   종료 없는 같은 라운드 수. 결론은 이 비교들의 CI에서만 고르고, config 그대로의 비교는 참고로만 싣는다.

## 결정
1. **point-in-time 추론을 1차 프로토콜로 삼는다** ((A)-2). answer_start 이전으로 로그 자체를 잘라낸 별도 로더로
   추론한다(cutoff 개념이 없는 코드에는 인자만 바꾸는 것으로 불충분하다). 팀 배포 코드의 추론 시점은 "2차(팀 방식
   추론 시점)" 행으로 남긴다 - **같은 point-in-time 학습 모델**에 추론 시점만 팀 방식으로 적용한 것이지, 팀 학습
   절차 전체의 재현이 아니다.
2. **정답 구간은 모든 arm/시드/버전이 공유하는 고정 시각 하나로 정의한다** ((B)-2).
3. **베이스라인을 모델과 같은 로그/후보 풀/정답 구간으로 병기하고, 모델-베이스라인 쌍 CI로 판정한다** ((C)-2).
   cold/warm 분리, 이미 클릭한 아이템을 뺀 seen 필터, 이전에 노출된 아이템(클릭 여부 무관)을 모두 뺀 unshown 필터를
   모델과 베이스라인 양쪽에 보고한다. 히스토리가 없는 유저의 폴백은 명시하고(현재 popularity), 후보 리스트 순서
   같은 임의 순서를 폴백으로 쓰지 않는다.
4. **조기 종료는 학습 구간 내부의 inner-validation만 쓰고, 검증 행을 고정 시드로 섞어 넘긴다 ((D)-3).** 순위 지표로
   조기 종료할 때 검증 행의 순서가 라벨과 상관되면 안 된다. `best_iteration`, distinct score 수, 평가 유저별 최고점 동점
   크기, 동점 진단을 항상 기록하고, 동점 무작위 추첨 결과와 고정 라운드 민감도를 함께 낸다. `best_iteration`이 5 이하인
   시드는 표시하고, 섞은 뒤에도 그런 시드가 남는 arm의 효과는 그 표시와 함께만 읽는다.
5. **다중 시드 + nested bootstrap(시드 x 유저)을 기본으로 하되, 같은 모델을 공유하는 비교는 시드를 쌍으로
   재표본한다** ((E)-3). 유저 수와 시드 수를 결과표에 항상 적고, 다중비교 보정을 하지 않았으면 그렇다고 밝힌다.
6. **정확도 주장은 공개 벤치마크에서만 한다** ((F)-2). EB-NeRD(1차, `data/benchmarks/ebnerd` - 라이선스상 이 Mac 밖으로
   복사 금지)를 기본으로, MIND를 보조로 검토한다. 한국어 합성 스냅샷의 절대 지표는 "성능"으로 인용하지 않는다.
7. 각 코드 버전의 **`config.yaml`을 그대로 읽어** 쓰고(시간/출력 경로 등 재현에 필요한 필드만 덮어쓴다), 실제 쓰인
   objective와 config 해시를 결과에 기록한다. v1은 fix-snapshot을 실제 config(`lambdarank`)가 아니라 하드코딩된
   `binary`로 돌려 그 버전이 아닌 모델을 평가했다 - 이건 정의상의 오류라 고친 것이고, 두 설정의 통제된 성능 비교는
   하지 않았다.
8. **캐시 키는 실행되는 코드의 내용 해시, 데이터 sha256, answer_start, top_k, 추첨 횟수, 라운드 정책, 검증 행 순서를
   포함하고 ((H)-2), 작업 트리가 dirty면 최종 결과를 쓰지 않는다.** 이것은 옛 결과를 모르고 재사용할 위험을 줄일 뿐 없애지는
   않는다(예: 파이썬 패키지 버전, 아카이브 버전의 `src/` 밖 파일은 키에 없다).
9. **리포트의 결론 단어는 CI 부호로 자동 선택한다** ((G)-2). 외부 수치(팀 보고값 0.897 등)는 인용할 때마다 출처와
   검증 가능 여부를 함께 적고, 기록이 없는 것(측정 절차·시점)은 없다고 적는다. 이력서용 문장에는 팀에 대한 귀속이나
   모델 소유 주장을 넣지 않는다. **이상 현상의 원인은 측정으로 확인한 것만 적는다** - 확인하지 못했으면 '원인 미확인'으로
   남긴다(v2.1은 1라운드 종료의 원인을 추정으로 적었다가 틀렸다).
10. **같은 조건끼리만 비교한다.** 학습과 평가를 동시에 바꾸는 arm(padded_400: 사본이 학습 negative에도 섞임)은 효과로
    보고하지 않고, 정답 집합이 다른 두 조건(작은 풀 vs 전체 풀)의 차이를 '효과'로 계산하지 않는다 - 작은 풀은 같은 풀·
    같은 정답 위의 베이스라인과만 비교한다. 여러 요인이 함께 바뀌는 arm(impression negative)은 바뀌는 요인을 나열한다.
    **코드 버전 비교도 같다 ((I)-2)**: objective와 조기 종료 방식이 같은 쌍, 그리고 조기 종료 없이 같은 라운드 수로
    학습한 쌍으로 비교하고, 각 쌍에 남는 차이를 적는다. 결론은 이 쌍들의 CI가 모두 같은 방향일 때만 그 방향으로 쓴다.

## 결과와 한계
**긍정적:**
- point-in-time 프로토콜은 로그 자체를 잘라내므로 cutoff 개념이 없는 코드에도 엔진 수정 없이 적용된다.
- 모델과 베이스라인이 같은 저울 위에 있고 쌍 CI로 판정하므로, "모델이 낫다"는 주장이 필요한 증거를 갖췄는지 항상 확인할 수 있다.
- 결론 단어가 CI에서 나오므로 숫자가 바뀌면 문장도 바뀐다. v2.2 재실행에서 실제로 그랬다: 'popularity 대비 P@5 열위'와
  '2차 격차 양수'가 '검출 안 됨'으로 바뀌었다.
- 동점 진단을 실행마다 남기므로, 조기 종료가 일찍 멈췄을 때 지표 탓인지를 추정이 아니라 기록으로 가릴 수 있다.
- 내용 해시 캐시 키와 dirty 거부로 커밋 안 된 코드의 결과가 옛 키로 섞이는 위험이 줄었다(없어진 것은 아니다).

**한계:**
- **엔진은 고치지 않았다.** `main_lgbm.py`의 운영 학습 경로는 지금도 positive가 그룹 첫 행인 검증 프레임에 NDCG 조기
  종료를 쓴다. 이 아카이브에서 그 순서로 조기 종료하면 5개 시드 중 3개가 트리 1개 모델이다. 하네스는 재현 대상 코드를
  바꾸지 않으므로, 엔진 쪽 수정(검증 그룹 행 섞기 또는 동점에 영향받지 않는 조기 종료 지표)은 별도 변경으로 남는다
  ([ADR 0003](0003-lightgbm-mmr-for-recommendation.md)의 한계 항목).
- 섞기는 한 번의 추첨이다. 동점 행의 순서를 무작위로 만들 뿐 기대값으로 조기 종료하는 것은 아니어서 잡음이 남는다. 검증
  그룹 1,432개에서 섞은 순서의 NDCG@5와 동점 기대값의 차이는 1라운드에서 최대 0.003, 고른 라운드에서 최대 0.001이었고,
  LightGBM이 섞은 순서에서 본 '고른 라운드 − 1라운드' 차이는 최소 0.018이었다 - 이 데이터에서는 추첨이 결론을 뒤집을
  크기가 아니지만, 검증 그룹이 적은 데이터에서는 다를 수 있다. 학습 프레임의 행 순서는 엔진 그대로다 - lambdarank의 람다
  계산도 점수가 같은 행의 순위를 행 순서로 정하지만 그 영향은 분리하지 않았다.
- 섞은 뒤에도 조기 종료가 5라운드 이하에서 멈추는 arm이 있고(impression, generator_split 일부 시드) 원인을 확인하지 않았다.
- 버전 비교에서 '같은 조건'은 두 가지뿐이다. 둘 다 100라운드인 비교는 objective가 여전히 다르고, 둘 다 binary인 비교는
  current에 objective만 덮어쓴 것이라 current의 실제 설정이 아니다. 두 비교 모두 검출되지 않았다는 것은 n=31명·시드
  5개에서의 판단 불가이지 차이가 없다는 증거가 아니다.
- 일부 학습 쪽 입력은 여전히 전체 로그를 본다: team-final 학습 피처의 전역 히스토리, 모든 버전의 negative sampler 제외
  집합. 재검토자가 제외 집합을 answer_start 이전으로 제한해 따로 돌린 결과 효과는 검출되지 않았다(MRR −0.014 [−0.119, +0.085],
  3시드 - 이 저장소 실행이 아닌 검토자 수치).
- 클릭 라벨 자체의 품질(LLM 생성, 순환성 가능성)은 고치지 못한다 - 공개 벤치마크 교차검증(결정 6)이 필요한 이유다.
- 세션이 몇 시간뿐인 로그에서 point-in-time 경계를 두면 평가 유저의 절반(31명 중 15명)이 히스토리가 없는 cold 유저가 된다.
  데이터가 실제로 그렇다는 신호이며, cold/warm을 나눠 보고하는 이유다.
- nested bootstrap은 시드 3~5개 위의 재표본이라 학습 무작위성을 거칠게만 반영하고, 유저도 31명이라 구간이 넓다. 수십 개 구간을
  보정 없이 병기하므로 개별 구간 하나를 '유의함'으로 읽지 않는다.
- EB-NeRD/MIND 교차검증은 결정만 했고 아직 실행하지 않았다.
- **리포트의 current 수치는 main 위로 옮기기 전의 엔진으로 낸 것이다 - 재실행 대기(클라우드).** 옮긴 뒤 current 엔진의
  내용 해시가 달라졌고(증거의 '옮긴 뒤의 출처' 항목), 표본 대조 10회는 같았지만 68회 전체 재실행은 하지 않았다. 상수
  피처 제거를 얹으면 해시가 한 번 더 달라지고 이번에는 모델 입력 열이 바뀐다(증거의 '상수 피처 제거를 얹은 뒤의 출처'
  항목). 그 표본 대조 10회도 같았지만 전체 재실행은 하지 않았다. 명령은
  아래와 같고, 첫 줄을 종료 코드 0이 나올 때까지 반복한 뒤 둘째 줄로 리포트를 만든다:
  `TEAM_REPRO_RESULTS_DIR=<dir> TEAM_REPRO_ARCHIVE_ROOT=<dir> .venv/bin/python evaluation/recsys/team_repro/run_repro.py --max-new-runs 10`,
  `.venv/bin/python evaluation/recsys/team_repro/make_report_v2.py`.
  이 저장소만으로는 다시 돌릴 수 없다: `data/team_archive`는 gitignore 대상이고, 코드 버전을 가리키는 tag `team-final`과
  브랜치 `port/fix-snapshot`은 원격에 없으며(team-final의 커밋 자체는 main 이력에 있다), `file_loader.py`와
  `categories.py`의 `MAIN_CHECKOUT_ROOT`가 로컬 절대 경로로 고정돼 있다. 다른 머신에서 돌리려면 이 경로를 먼저 바꿔야 하고,
  바꾸면 하네스 입력 해시가 달라지므로 전체 재실행과 함께 해야 한다.
