# ADR 0007: 추천 시스템 오프라인 평가 프로토콜

## 상태
채택됨 (2026-09-25). 개정 (2026-09-26): team_repro v2 재검토를 반영해 증거를 실측 수치로 바꾸고, 시드 수·캐시·
조기 종료에 관한 과장을 고쳤다. 결정 4·5·7·8을 수정하고 결정 9·10을 추가했다.

## 컨텍스트
`evaluation/recsys/team_repro`는 팀이 아카이브해 둔 합성 데이터(`data/team_archive`, gitignored) 위에서
team-final(팀 최종 코드) / fix-snapshot(자체 리뷰 중간 수정본) / current(이 브랜치) 세 코드 버전을 그대로
재실행·비교하는 파일 기반 하네스다. 추천 모델(LightGBM+MMR)은 팀원이 담당한 부분이고, 이 하네스와 평가는
그 모델을 재현·검증하는 작업이다.

v1 리포트([`reports/recsys/team_repro_v1.md`](../../reports/recsys/team_repro_v1.md))는 어드버서리얼 방법론
검토에서 "unsound" 판정을 받았다. 핵심 원인은 추론 시점에 정답 구간의 클릭이 유저 히스토리 피처에 섞여 들어간
것(inference-time leakage)이었다. v2는 재검토에서 "sound-with-caveats"를 받았지만 blocker 2건이 남았다.
(1) team-final-as-written 행이 노출 행 전체를 정답으로 세어 무작위도 MRR 1.0이 되는 정의 오류였는데 이를 팀
보고값 0.897에 "근접"하다고 썼다. (2) 이력서 문장이 팀에 사실이 아닌 귀속을 했다. major 4건도 있었다. 조기 종료
모델이 여전히 트리 1개로 붕괴했고, 후보 풀 arm이 서로 다른 조건을 비교했고, 이 ADR 자체가 시드 수와 캐시
보장을 과장했다. 이 ADR은 두 차례 검토에서 드러난 문제를 근거로, 이 저장소의 추천 시스템 오프라인 평가가 따라야
할 프로토콜을 정한다. team_repro 하네스뿐 아니라 recommend_engine 자체나 다른 평가 스크립트에도 적용한다.

## 검토한 대안

### (A) 추론 기준 시각
1. **데이터셋 끝 시각(`pinned_now`)에 고정** (v1이 한 것, 그리고 `main_lgbm.py` 디버그 모드 `inference_pipeline`이
   하는 것 - `get_db_max_timestamp()`): 구현이 가장 단순하고 팀 배포 코드와 같지만, 검증 구간 로그가 있는 한
   히스토리 피처에 정답이 섞인다.
2. **고정된 point-in-time 경계(answer_start)** - 그 경계 이전으로 로그 자체를 물리적으로 잘라낸 뒤 피처를 다시
   계산한다.
3. **요청마다 실시간 "지금"** (온라인 서빙) - 정적 스냅샷 위의 오프라인 재현에서는 흉내낼 수 없다.

### (B) 검증(정답) 구간 정의
1. 각 실행이 자기 학습 데이터의 80% 지점을 다시 계산 (v1) - negative sampling에 따라 경계가 시드마다 몇 초씩 움직인다.
2. **모든 arm/시드/버전이 공유하는 단일 고정 시각** - 클릭 로그를 시간순 정렬해 뒤 20%를 자르는 경계를 한 번만 계산한다.

### (C) 베이스라인
1. 모델만 보고 상대적 개선을 주장 (v1은 베이스라인 표를 실었지만 모델 쪽에만 누출이 있어 비교가 불공정했다).
2. **모델과 같은 로그/후보 풀/정답 구간으로 계산한 random·popularity·recency·category_match·cosine_history·
   onboarding cosine 베이스라인을 필수로 병기**하고, 모델-베이스라인 쌍 CI로 판정한다.

### (D) 모델 선택(조기 종료)과 학습 붕괴
1. 정답 구간을 조기 종료 검증셋으로 재사용 (v1, `main_lgbm.py` 원본) - 모델이 정답을 보고 트리 수를 고른다. v1에서
   `best_iteration`이 5개 시드 중 3개에서 1이었다.
2. 학습 구간 자체를 시간순으로 나눈 inner-validation으로만 조기 종료 (v2).
3. **2에 더해, 트리 1개로 멈춘 시드를 '퇴화'로 표시하고, 동점 무작위 추첨과 조기 종료 없는 고정 라운드 학습을
   민감도로 함께 보고** (v2.1). inner-validation은 1의 문제(정답으로 모델 고르기)는 없앴지만 붕괴는 고치지
   못했다: current lambdarank는 v2.1에서도 5개 시드 중 3개가 `best_iteration`=1이었고, 이런 시드는 서로 다른
   점수가 27~30개뿐이라 순위가 뉴스레터 CSV 행 순서로 정해졌다.
4. 최소 라운드나 learning_rate를 바꿔 붕괴 자체를 막기 - 재현 대상(팀·자체 수정 코드의 설정)을 바꾸는 것이라
   이 하네스의 1차 행에는 쓰지 않는다. 대신 사전 선언한 고정 100라운드를 민감도 arm으로 둔다.

### (E) 신뢰구간
1. 유저만 재표본하는 bootstrap (v1) - 시드 간 변동이 구간에 반영되지 않는다.
2. 시드 x 유저를 함께 재표본하는 nested bootstrap (v2) - 두 조건이 같은 학습 모델을 공유할 때도 시드를 따로
   재표본해 구간이 과하게 넓었다.
3. **2에 더해, 같은 모델을 공유하는 비교(추론 방식만 다른 누출 효과)는 시드를 쌍으로 재표본** (v2.1).

### (F) 정확도 주장의 근거 데이터
1. 이 합성 아카이브(100 페르소나, LLM이 만든 클릭)만으로 절대 성능을 주장한다 - 클릭 라벨이 `category_match` 같은
   명시적 신호와 순환성이 있을 수 있고, 세션이 6시간16분뿐이라 신선도 피처가 무의미하다.
2. **공개 벤치마크(EB-NeRD 1차, MIND 보조)에서 같은 파이프라인의 상대 효과가 재현되는지 확인한 뒤에만 정확도를
   주장**하고, 이 합성 스냅샷은 화이트박스 진단으로만 쓴다.

### (G) 리포트의 결론 문장
1. 결론 문장을 사람이 미리 써 두고 숫자만 채운다 (v2) - 숫자가 바뀌어도 문장이 그대로라 MRR 1.0을 "0.897에 근접"이라고
   썼다.
2. **결론 단어를 CI 부호에서 자동으로 고른다** - `metrics.ci_verdict()`가 positive/negative/inconclusive를 돌려주고,
   리포트 생성기는 그 값으로만 "부풀린다/검출되지 않는다", "모델 우위/열위/구분 안 됨"을 고른다.

### (H) 실행 캐시 키
1. 하네스·엔진의 HEAD git SHA + config 해시 (v2) - 커밋 안 된 수정이 옛 SHA 키로 캐시됐다(v1 SHA 키 아래 v2 형식
   결과 10건). 데이터·answer_start·top_k도 키에 없었고, 코드 아카이브는 존재 여부만 확인했다.
2. **실제 실행되는 파일의 내용 해시 + 데이터 sha256 + answer_start/top_k/추첨 횟수/라운드 정책**, 아카이브는 ref
   SHA가 바뀌면 다시 풀고, 감시 경로가 dirty면 최종 JSON을 쓰지 않는다.

## 결정
1. **point-in-time 추론을 1차 프로토콜로 삼는다** ((A)-2). answer_start 이전으로 로그 자체를 잘라낸 별도 로더로
   추론한다(cutoff 개념이 없는 코드에는 인자만 바꾸는 것으로 불충분하다). 팀 배포 코드의 추론 시점은 "2차(팀 방식
   추론 시점)" 행으로 남긴다 - **같은 point-in-time 학습 모델**에 추론 시점만 팀 방식으로 적용한 것이지, 팀 학습
   절차 전체의 재현이 아니다.
2. **정답 구간은 모든 arm/시드/버전이 공유하는 고정 시각 하나로 정의한다** ((B)-2).
3. **베이스라인을 모델과 같은 로그/후보 풀/정답 구간으로 병기하고, 모델-베이스라인 쌍 CI로 판정한다** ((C)-2).
   cold/warm 분리, 이미 클릭한 아이템을 뺀 seen 필터, 이전에 노출된 아이템(클릭 여부 무관)을 모두 뺀 unshown 필터를
   모델과 베이스라인 양쪽에 보고한다. 히스토리가 없는 유저의 폴백은 명시하고(현재 popularity), 후보 리스트 순서
   같은 임의 순서를 폴백으로 쓰지 않는다.
4. **조기 종료는 학습 구간 내부의 inner-validation만 쓰고 ((D)-3), 트리 1개로 멈춘 시드는 '퇴화'로 표시한다.**
   `best_iteration`, distinct score 수, 평가 유저별 최고점 동점 크기를 항상 기록하고, 동점 무작위 추첨 결과와 고정
   라운드 민감도를 함께 낸다. 퇴화 시드가 섞인 arm의 효과는 모델 효과로 해석하지 않는다.
5. **다중 시드 + nested bootstrap(시드 x 유저)을 기본으로 하되, 같은 모델을 공유하는 비교는 시드를 쌍으로
   재표본한다** ((E)-3). 유저 수와 시드 수를 결과표에 항상 적고, 다중비교 보정을 하지 않았으면 그렇다고 밝힌다.
6. **정확도 주장은 공개 벤치마크에서만 한다** ((F)-2). EB-NeRD(1차, `data/benchmarks/ebnerd` - 라이선스상 이 Mac 밖으로
   복사 금지)를 기본으로, MIND를 보조로 검토한다. 한국어 합성 스냅샷의 절대 지표는 "성능"으로 인용하지 않는다.
7. 각 코드 버전의 **`config.yaml`을 그대로 읽어** 쓰고(시간/출력 경로 등 재현에 필요한 필드만 덮어쓴다), 실제 쓰인
   objective와 config 해시를 결과에 기록한다. v1은 fix-snapshot을 실제 config(`lambdarank`)가 아니라 하드코딩된
   `binary`로 돌려 그 버전이 아닌 모델을 평가했다 - 이건 정의상의 오류라 고친 것이고, 두 설정의 통제된 성능 비교는
   하지 않았다.
8. **캐시 키는 실행되는 코드의 내용 해시, 데이터 sha256, answer_start, top_k, 추첨 횟수, 라운드 정책을 포함하고
   ((H)-2), 작업 트리가 dirty면 최종 결과를 쓰지 않는다.** 이것은 옛 결과를 모르고 재사용할 위험을 줄일 뿐 없애지는
   않는다(예: 파이썬 패키지 버전, 아카이브 버전의 `src/` 밖 파일은 키에 없다).
9. **리포트의 결론 단어는 CI 부호로 자동 선택한다** ((G)-2). 외부 수치(팀 보고값 0.897 등)는 인용할 때마다 출처·측정
   시점·검증 가능 여부를 함께 적고, 이력서용 문장에는 팀에 대한 귀속이나 모델 소유 주장을 넣지 않는다.
10. **같은 조건끼리만 비교한다.** 학습과 평가를 동시에 바꾸는 arm(padded_400: 사본이 학습 negative에도 섞임)은 효과로
    보고하지 않고, 정답 집합이 다른 두 조건(작은 풀 vs 전체 풀)의 차이를 '효과'로 계산하지 않는다 - 작은 풀은 같은 풀·
    같은 정답 위의 베이스라인과만 비교한다. 여러 요인이 함께 바뀌는 arm(impression negative)은 바뀌는 요인을 나열한다.

## 증거
`team_repro` v2.1 실행([`reports/recsys/team_repro_v2.md`](../../reports/recsys/team_repro_v2.md), 원자료
`team_repro_v2.json`): 고정 answer_start `2026-01-31T00:07:44`, 평가 유저 31명(합성), 시드 current·team-final과
current의 모든 분해 arm 5개(42~46), fix-snapshot 3개(42~44), 부트스트랩 1000회. 괄호는 95% CI이고 다중비교 보정은 없다.

- **추론 시점 누출 (결정 1).** 같은 모델의 2차 − 1차 MRR: current +0.176 [+0.076, +0.285](0.753 → 0.577),
  team-final +0.285 [+0.158, +0.418](0.848 → 0.564), fix-snapshot +0.208 [+0.098, +0.335] (시드 쌍 재표본).
- **v1의 버전 격차.** team-final − current MRR: 1차 −0.014 [−0.129, +0.091](검출 안 됨), 2차 +0.096 [+0.032, +0.170],
  누출 효과의 차이 +0.109 [+0.012, +0.211]. 격차는 팀 방식 추론 시점에서만 나타난다. 인과 문장("격차의 주된 원인")으로는
  쓰지 않는다.
- **베이스라인 (결정 3).** current − popularity P@5 −0.133 [−0.245, −0.014]. MRR은 popularity·onboarding cosine·
  cosine_history와 구분되지 않는다. unshown 필터 양쪽 적용 시 popularity 대비 MRR +0.151 [+0.024, +0.291], cosine_history
  대비 P@5 −0.132 [−0.250, −0.006]로 필터에 따라 판정이 바뀐다 - 모델 우위 주장은 성립하지 않는다.
- **학습 붕괴 (결정 4).** current lambdarank 조기 종료: `best_iteration` [35, 1, 1, 90, 1], 퇴화 3/5. 퇴화 시드는 평가
  유저당 최고점 동점 아이템이 중앙값 33~51개. 동점을 무작위로 깨면 MRR 0.577 → 0.551(범위 0.335~0.655). CSV 행 순서
  고정 리스트만으로 MRR 0.638. 고정 100라운드 0.618±0.015, binary(퇴화 0/5) 0.587±0.037.
- **학습 시점 히스토리 누출(FIX #4)의 분해 (결정 4의 이유).** leaky − fixed MRR: lambdarank 조기 종료 −0.017 [−0.105, +0.066],
  binary −0.130 [−0.259, −0.019], lambdarank 100라운드 −0.076 [−0.160, +0.007]. 붕괴한 모델 위에서만 분해했다면 검출된
  binary의 효과를 놓쳤을 것이다. FIX #4/#5는 팀 프로젝트 이후 자체 리뷰에서 나온 수정이다.
- **팀 정답 정의 (결정 9).** team-final 스크립트의 창(NOW()-6일)을 이 아카이브(6시간16분)에 옮기면 창 안의 클릭이 학습
  구간을 포함한 로그 전체가 된다: team-final MRR 0.989, **같은 정의의 무작위 0.652**(P@5 0.476). v2가 쓴 노출 행 전체
  정의에서는 무작위도 1.0이다. 팀 보고값 0.897(103명/405건 스냅샷에서 한 시점에 측정, 누출로 부풀려졌을 가능성, 검증
  불가)과 방향은 일관되지만 그 값을 재현·설명하지 않는다.
- **재현성 (결정 7·8).** 같은 시드를 공유하는 8개 arm(헤드라인 3버전·leaky·binary·small_recent_15·generator_split 2버전)의
  MRR/P@5가 v2 원자료(커밋 `1585ce6`)와 소수 4자리까지 같다. impression arm은 inner 분할 수정으로 달라졌다(정상). 최종 JSON은
  작업 트리가 깨끗한 상태(`d4b9878`)에서 기록됐다.

## 결과와 한계
**긍정적:**
- point-in-time 프로토콜은 로그 자체를 잘라내므로 cutoff 개념이 없는 코드에도 엔진 수정 없이 적용된다.
- 모델과 베이스라인이 같은 저울 위에 있고 쌍 CI로 판정하므로, "모델이 낫다"는 주장이 필요한 증거를 갖췄는지 항상 확인할 수 있다.
- 결론 단어가 CI에서 나오므로 숫자가 바뀌면 문장도 바뀐다.
- 내용 해시 캐시 키와 dirty 거부로 커밋 안 된 코드의 결과가 옛 키로 섞이는 위험이 줄었다(없어진 것은 아니다).

**한계:**
- **학습 붕괴는 해결되지 않았다.** inner-validation 조기 종료 lambdarank는 여전히 5개 중 3개 시드가 트리 1개다. 이 프로토콜은
  붕괴를 표시하고 민감도를 낼 뿐이며, 붕괴 원인(작은 inner-valid, 첫 트리 이후 이득 없음 등)을 고치는 것은 별도 작업이다.
- 일부 학습 쪽 입력은 여전히 전체 로그를 본다: team-final 학습 피처의 전역 히스토리, 모든 버전의 negative sampler 제외
  집합. 재검토자가 제외 집합을 answer_start 이전으로 제한해 따로 돌린 결과 효과는 검출되지 않았다(MRR −0.014 [−0.119, +0.085],
  3시드 - 이 저장소 실행이 아닌 검토자 수치).
- 클릭 라벨 자체의 품질(LLM 생성, 순환성 가능성)은 고치지 못한다 - 공개 벤치마크 교차검증(결정 6)이 필요한 이유다.
- 세션이 몇 시간뿐인 로그에서 point-in-time 경계를 두면 평가 유저의 절반(31명 중 15명)이 히스토리가 없는 cold 유저가 된다.
  데이터가 실제로 그렇다는 신호이며, cold/warm을 나눠 보고하는 이유다.
- nested bootstrap은 시드 3~5개 위의 재표본이라 학습 무작위성을 거칠게만 반영하고, 유저도 31명이라 구간이 넓다. 수십 개 구간을
  보정 없이 병기하므로 개별 구간 하나를 '유의함'으로 읽지 않는다.
- EB-NeRD/MIND 교차검증은 결정만 했고 아직 실행하지 않았다.
