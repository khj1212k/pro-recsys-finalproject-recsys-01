# ADR 0017: 단기 사용자 상태 저장소 - 별도 저장소 없이 클릭 로그에서 요청마다 계산한다

## 상태
채택됨 (2026-10-06). 지연은 합성 데이터로 CI 러너에서 쟀다. 배포 대상(arm64 2 OCPU)에서는 재지 않았다.

번호 메모: 계획 문서 초안이 0017을 다른 주제(콜드스타트·언어 전이 계약)에 배정한 적이 있다. 코드가 이
번호를 먼저 썼으므로 그 주제는 다른 번호를 받는다.

## 컨텍스트
- 요청 시점 추천(ADR 0015)은 사용자의 "방금 한 행동"을 단기 선호 벡터로 쓴다: **최근 24시간 안의 최근
  20클릭**에 해당하는 뉴스레터 임베딩의 평균. 클릭한 직후의 다음 요청에 반영되어야 한다.
- 클릭은 이미 `POST /logs/newsletter/click`이 `user_newsletter_ctr_log`에 한 행씩 쓴다. 이 테이블이 클릭의
  원본이고 `(user_id, created_at DESC)` 인덱스가 있다(ADR 0008).
- API 워커는 여러 개일 수 있고 재시작된다. 상시 구성요소는 PostgreSQL 하나뿐이다(ADR 0006).

## 검토한 대안

"읽기"는 사용자 한 명의 단기 벡터를 얻는 데 걸리는 시간, "쓰기"는 클릭 한 번을 반영하는 데 걸리는 시간이다.
수치는 아래 증거 1의 세 실행(R1, R2, R3)의 p50이다.

| 대안 | 읽기 p50 (ms) | 쓰기 p50 (ms) | 클릭 원본과의 관계 |
|---|---|---|---|
| 1. **PostgreSQL, DB에서 평균 (채택)** | 0.55~0.75 | 0.66~0.87 (클릭 INSERT, 어차피 하는 일) | 원본 그 자체 |
| 2. PostgreSQL에서 ID만 읽고 프로세스 내 아이템 캐시로 평균 | 0.31~0.43 | 위와 같음 | 원본 그 자체 |
| 3. Redis 리스트(LPUSH/LTRIM/EXPIRE) + 아이템 캐시 | 0.19~0.29 | 0.16~0.26 **추가** | 사본. 이중 쓰기 필요 |
| 4. 프로세스 내 deque | 0.017~0.024 | 0.001 **추가** | 워커마다 다른 사본 |

1. **PostgreSQL, DB에서 평균 (채택)** - 쿼리 하나(`vector_send(AVG(embedding))`, 클릭 로그 인덱스 스캔 +
   뉴스레터 PK 조인)로 끝난다. 쓰기 경로를 바꾸지 않고, 워커 수나 재시작과 무관하게 맞는 값을 준다.
2. ID만 읽고 아이템 캐시로 평균 - 0.3ms쯤 빠르다. 하지만 클릭한 뉴스레터가 아이템 캐시에 있어야 한다.
   캐시는 신선도 창(72시간) 안의 추천 후보로 채워지는데, 최근 24시간에 클릭한 뉴스레터는 그 창 밖의
   것일 수 있어 캐시 미적중 처리가 따로 필요하다. 요청 하나가 11~16ms(1 클라이언트 p50, ADR 0015 증거 3)인
   경로에서 0.3ms를 얻자고 경우를 하나 늘리지 않는다.
3. Redis 리스트 - 읽기가 0.36~0.46ms 빠르다. 대가는 (a) 상시 구성요소 하나, (b) 클릭마다 PostgreSQL INSERT에
   **더해** Redis 쓰기, (c) 두 저장소가 어긋났을 때(한쪽 쓰기 실패, Redis 재시작)의 복구 규칙이다.
   클릭 로그는 평가와 학습의 원본이라 PostgreSQL 쓰기를 없앨 수 없으므로 Redis는 쓰기 비용을 줄이지 못한다.
4. 프로세스 내 deque - 가장 빠르다. 하지만 클릭을 받은 워커만 그 클릭을 알고, 재시작하면 사라진다.
   워커가 둘 이상이면 틀린 값을 준다.

## 결정
- 단기 벡터는 저장하지 않는다. 결과 캐시가 적중하지 않은 요청마다 `SqlRecsysRepository.short_term_vector`가
  클릭 로그에서 계산한다(창 24시간, 최대 20클릭, 가중치 없는 평균. `RECSYS_SHORT_TERM_HOURS`,
  `RECSYS_SHORT_TERM_MAX_CLICKS`).
- "클릭이 있었는가"는 결과 캐시 키 `(user_id, last_click_id)`로 감지한다. 클릭이 들어오면 키가 바뀌어 다음
  요청이 단기 벡터부터 다시 계산한다(ADR 0015 대안 8).
- Redis는 도입하지 않는다. 아래 "다시 볼 조건"에 닿으면 대안 3을 다시 검토한다.

## 증거

### 1. 규모 벤치마크 (CI, 합성 데이터)
`evaluation/serving/request_path_bench.py`의 `short_term_store` 절. 결과 원본은 `reports/serving/`에 있고
실행 조건은 ADR 0015 증거 3과 같다(GitHub 호스티드 러너 x86_64 4 vCPU, PostgreSQL 16 + pgvector와 Redis 7
서비스 컨테이너, 클릭 1,015,000건, 최근 24시간 활동 사용자 8,664명). "헤비"는 최근 24시간에 30번 클릭해
LIMIT 20이 꽉 차는 사용자 500명, "활동"은 최근 24시간에 한 번 이상 클릭한 사용자다. 대안 2~4는 같은
사용자에 대해 미리 채운(warm) 아이템 임베딩 캐시를 쓴다. p50 / p95 ms:

| 측정 | n | R1 (36168597131) | R2 (37348628265) | R3 (37350694155) |
|---|---|---|---|---|
| PostgreSQL DB 평균, 헤비 | 400 | 0.720 / 0.771 | 0.554 / 0.649 | 0.751 / 1.108 |
| PostgreSQL DB 평균, 활동 | 400 | 0.484 / 0.702 | 0.397 / 0.575 | 0.525 / 0.738 |
| PostgreSQL ID + 아이템 캐시, 헤비 | 400 | 0.398 / 0.421 | 0.307 / 0.413 | 0.430 / 0.463 |
| Redis 리스트 + 아이템 캐시, 헤비 | 400 | 0.264 / 0.285 | 0.193 / 0.273 | 0.290 / 0.327 |
| 프로세스 내 deque, 헤비 | 400 | 0.021 / 0.028 | 0.017 / 0.024 | 0.024 / 0.034 |
| 쓰기: PostgreSQL 클릭 INSERT + COMMIT | 80 | 0.709 / 0.814 | 0.656 / 0.769 | 0.874 / 1.109 |
| 쓰기: Redis LPUSH + LTRIM + EXPIRE | 80 | 0.189 / 0.268 | 0.155 / 0.273 | 0.259 / 0.296 |
| 쓰기: 프로세스 내 deque | 400 | 0.001 / 0.002 | 0.001 / 0.001 | 0.001 / 0.001 |

- 채택안과 가장 빠른 공유 저장소(Redis)의 차이는 읽기 p50 기준 0.36~0.46ms다. 요청 하나의 p50
  11~16ms(1 클라이언트)에서 3% 안팎이다.
- 쿼리 계획(EXPLAIN ANALYZE, 세 실행 같은 계획, 실행 0.27~0.37ms): `Aggregate > Limit > Nested Loop >
  Index Scan[ix_user_newsletter_ctr_log_user_id_created_at] > Index Scan[news_letter_pkey]`. 클릭 로그
  전체(100만 행)를 훑지 않는다.
- 세 실행은 서로 다른 러너 VM이고 같은 코드에서도 약 20% 흔들린다(R1과 R2). 순서(프로세스 내 < Redis <
  PostgreSQL ID < PostgreSQL DB 평균)는 세 실행에서 같았다.

### 2. 동작 (CI 통합 테스트, `tests/integration/test_realtime_recsys_seeded_db.py`)
- 30시간 전의 클릭만 있는 사용자의 단기 벡터는 없다(None).
- 다른 주제를 클릭하면 다음 응답에서 그 주제의 비율이 늘고(0.00 -> 0.10, 상위 10개 중) 결과 캐시는
  적중하지 않는다. 효과의 크기와 그 한계는 ADR 0015 증거 2·4에 있다.

## 결과와 한계
- 상시 구성요소가 늘지 않았고 클릭의 원본이 하나로 남았다.
- 재지 않은 것:
  - 배포 대상(arm64 2 OCPU)에서의 값. 재실행 대기(클라우드) - ADR 0015 "결과와 한계"의 명령과 같다.
  - PostgreSQL과 Redis가 API와 **다른 호스트**에 있을 때의 값. 벤치마크는 모두 같은 러너의 localhost다.
    네트워크 왕복이 붙으면 두 저장소 모두 느려지고 차이의 비율은 줄어든다.
  - 24시간에 수백 번 클릭하는 사용자. LIMIT 20과 인덱스 순서 덕분에 읽는 행 수는 같을 것으로 보지만 재지 않았다.
  - 클릭 로그가 지금의 수십 배(수천만 행)일 때.
- 평균은 가중치 없는 평균이다. 24시간 창 안에서 최근 클릭에 더 큰 가중치를 주지 않는다. 창 길이와 클릭 수
  상한(24시간, 20)은 **정한 값이지 검증한 값이 아니다** - 추천 품질에 대한 근거가 없다.
- 클릭 로그는 `timestamp without time zone` 컬럼이라 "24시간 전"의 해석이 세션 TimeZone이 같다는 전제에
  기대고 있다(ADR 0015 "알고 있는 한계").

**다시 볼 조건**
- 단기 벡터 쿼리의 p95가 시간 예산(300ms)의 수 %를 넘는다(지금은 0.65~1.11ms, 0.4% 미만).
- 읽기 복제본을 두게 된다. 복제 지연만큼 클릭 반영이 늦어지므로 "클릭 직후 반영"이 깨진다.
- 세션 단위 신호(체류 시간, 스크롤)처럼 클릭 로그에 없는 단기 상태가 필요해진다.
