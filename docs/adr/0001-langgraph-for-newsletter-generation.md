# ADR 0001: 뉴스레터 생성 워크플로우에 LangGraph 사용

## 상태
채택됨

## 컨텍스트
클러스터링된 기사 묶음을 뉴스레터로 만드는 과정은 단순 1회 변환이 아니라 다음과 같은 다단계 파이프라인이다:

1. 클러스터가 하나의 일관된 이슈인지 평가 (아니면 재분할/아웃라이어 제거 후 재시도)
2. LLM으로 본문 생성
3. 생성된 뉴스레터 품질 평가 (기준 미달이면 피드백을 담아 재생성)
4. 통과하면 임베딩 생성 → 문체 변환 → DB 저장

이 흐름은 조건부 분기(평가 결과에 따라 다른 경로)와 재시도 루프(최대 N회)를 포함하며, 각 단계의 입출력(state)을 다음 단계로 명시적으로 전달해야 한다.

## 검토한 대안
- **단순 Python 스크립트(if/for 루프)**: 빠르게 만들 수 있지만 재시도/분기 로직이 늘어날수록 상태 전달이 암묵적이고 테스트하기 어려워진다.
- **Celery 등 태스크 큐**: 비동기 분산 처리에는 적합하지만, 이 프로젝트 규모(배치 파이프라인, 단일 프로세스)에서는 과한 인프라이며 조건부 재시도 그래프 표현에 특화되어 있지 않다.
- **LangGraph**: 노드(함수)와 엣지(조건부 전이)로 그래프를 선언적으로 정의하고, `AgentState`로 상태를 명시적으로 관리한다. LLM 파이프라인의 평가-재시도 패턴에 특화되어 있다.

## 결정
단일 클러스터의 "평가 → 생성 → 평가 → 재시도" 서브그래프에 LangGraph를 사용한다.

**중요한 스코프 결정**: 여러 클러스터를 순회하는 상위 오케스트레이션(배치 전체의 시작/종료)은 LangGraph 그래프 안에 포함하지 않고, `pipeline/stages.py`의 `Stage5_NewsletterGeneration`이 클러스터마다 `compile_workflow()`로 그래프를 만들어 `app.invoke(state)`를 반복 호출하는 방식으로 처리한다. 초기 구현에는 이 경계가 코드에 명시되어 있지 않아(`should_continue_processing`/`finalize_workflow`라는, 이름상 다중 클러스터 순회를 암시하지만 실제로는 그래프에 등록되지 않은 죽은 코드가 남아있었다), 리뷰 과정에서 발견 후 정리하고 `graph.py`에 스코프를 명시하는 docstring을 추가했다.

## 결과
**긍정적:**
- 각 노드(`evaluate_cluster`, `generate_newsletter`, `evaluate_newsletter` 등)가 단일 책임을 가져 개별 테스트가 쉬움
- 재시도 조건(`route_after_cluster_fail`, `route_after_newsletter_eval`)이 그래프 엣지로 명시적으로 드러나 로직을 추적하기 쉬움
- `generation_history`를 상태에 누적해 "왜 재생성이 필요했는지"를 재현 가능하게 기록(`workflow/helpers.py`)

**부정적/한계:**
- LangGraph를 "단일 클러스터 서브그래프"로만 쓰고 다중 클러스터 순회는 밖에서 처리하는 구조라, 프레임워크의 잠재력을 온전히 활용하지 못한다는 인상을 줄 수 있음 — 왜 이런 경계를 그었는지 문서화가 반드시 필요했음(이번에 보완)
- 그래프 재시도 카운터(`cluster_retry_count`)가 초기 구현에서 증가하지 않는 버그가 있었음(수정 완료, `docs/fix-log-2026-07.md` #8) — 상태 관리가 명시적인 만큼, 상태 갱신을 빠뜨리면 조용히 버그가 됨
