# ADR 0015: 요청 시점 추천 - API 프로세스 안에서 후보 합집합·스코어·MMR을 요청마다 계산한다

## 상태
채택됨 (2026-10-06). 구조와 안전장치(시간 예산, 폴백, 풀 분리)는 측정과 테스트로 확인했다.
아래 세 가지는 **확인하지 않은 채로 채택**했고 "결과와 한계"에 다시 적는다.
- 추천 품질: 이 ADR의 수치는 전부 지연·동작이다. 품질 주장은 하지 않는다.
- 휴리스틱 가중치(장기 0.45 : 단기 0.35): 합성 코퍼스에서 고른 사전값이다. 튜닝한 값이 아니다.
- 배포 대상(Oracle A1, arm64 2 OCPU)과 HTTP 수준의 지연: 재지 않았다(재실행 대기).

## 컨텍스트
- `GET /newsletters/today`는 하루 한 번 배치가 써 둔 `news_letter_today_batch` 행만 읽었다. 그래서
  (1) 배치 이후 가입한 사용자는 빈 목록을 받았고, (2) 클릭이 다음 배치 전까지 추천에 반영되지 않았다.
- 규모는 작다. 팀 합성 데이터의 한 번 실행분이 뉴스레터 151~195개여서 72시간 신선도 창 안의 후보는
  500개 안팎이다. 데이터베이스는 PostgreSQL + pgvector 하나이고(ADR 0006), 배포 대상은 2 OCPU짜리
  서버 한 대다. Redis 같은 상시 구성요소를 더 두는 데에는 운영 비용이 든다.
- API는 FastAPI 동기 엔드포인트다. 요청은 인증 조회(`get_current_user`) 때부터 앱 커넥션 풀(기본 5+10)의
  커넥션 하나를 쥔다.
- 팀 시절의 추천기(LightGBM + MMR, ADR 0003)는 배치 경로다. 그 평가 수치는 ADR 0007에서 철회했고,
  랭커 v2는 ADR 0013에서 따로 다룬다(둘 다 이 문서보다 먼저 병합되는 PR에 들어 있다). 이 ADR은
  **서빙 구조**만 정한다.

귀속: MMR 재정렬(`MMRReranker`, `CategoryBasedMMRReranker`, 선호 카테고리 수별 λ 규칙)은 팀 시절
성승우 설계·구현이다. 이 ADR에서 그 코드에 한 일은 재사용과 탐욕 선택 루프의 벡터화(선택 결과 동일)뿐이다.

## 검토한 대안

### 1. 어디서 계산할 것인가
1. 배치 유지 + 빈 목록만 인기 목록으로 채우기 - 가장 싸다. 신규 유저 문제는 풀리지만 클릭이 다음
   배치까지 반영되지 않는 문제는 그대로다. `RECSYS_MODE=batch`로 남겨 뒀다(되돌리는 스위치).
2. **API 프로세스 안에서 요청마다 계산 (채택)** - 후보 500개 규모에서는 정확 KNN이 수 ms라 별도
   서비스가 필요 없다(증거 3). 대신 요청 경로에 DB 왕복 10번 안팎과 numpy 계산이 들어가므로 시간
   예산과 폴백이 필요해진다.
3. 별도 추천 서비스(또는 워커 + 큐) - 프로세스가 하나 더 생기고 서비스 간 호출이 실패 지점이 된다.
   2 OCPU 한 대에서는 얻는 것이 없다. 요청 처리량이 프로세스 하나의 한계(증거 3)를 넘을 때 다시 본다.

### 2. 후보 생성
1. KNN 하나만 - 프로필과 비슷한 것만 나오고, 프로필이 없는 사용자에게는 후보가 없다.
2. **생성기 다섯 개의 합집합 (채택)**: 신선도 창(72시간) 안에서 프로필 KNN 100, 단기 벡터 KNN 100,
   최신 100, 인기 100, 선호 카테고리 최신 50. 중복을 빼고 300개에서 자르되 **라운드로빈**으로 합쳐
   한 생성기가 자리를 독식하지 않게 한다. 사용자가 이미 클릭한 항목은 뺀다.
3. ANN 인덱스(HNSW/IVFFlat) - 지금 규모에서는 `created_at` 인덱스로 창을 좁힌 뒤 정확 계산하는
   쪽이 2.1~2.8ms다(증거 3). 인덱스 유지 비용과 재현율 손실을 감수할 이유가 없다. 창 안의 행이
   지금의 수십 배가 되면 다시 본다.

여기서 "인기"는 **클릭 수가 아니다**. 배치 인기 랭킹과 같은 식
`exp(-age_hours/48) + log1p(raw_news_count)/5`, 곧 최신성 + 뉴스레터에 묶인 기사 수(클러스터 크기)다
(`app/recsys/popularity.py`). 클릭 기반 인기도는 아직 없다.

### 3. 스코어링
1. **`Scorer` 인터페이스 + `HeuristicScorer` (지금 활성)**:
   `0.45·cos(장기) + 0.35·cos(단기) + 0.15·exp(-age/48h) + 0.05·min(1, log1p(기사 수)/5)`.
   한쪽 벡터가 없으면 그 가중치를 다른 쪽으로 넘겨 개인화 비중 0.8을 유지한다. 가중치를 고른
   과정과 그 한계는 증거 4에 있다.
2. **`LightGBMScorer` 어댑터 (연결부만, 꺼져 있음)**: `model_registry` 테이블의 활성 모델을 60초마다
   확인해 바뀌면 다시 읽는다. 피처 함수는 서빙 코드에 두지 않고 `RECSYS_FEATURE_FN="모듈:함수"`로
   주입받는다 - 학습 쪽 피처 코드를 서빙에 복제하면 train/serve 불일치가 생기기 때문이다. 피처 함수나
   활성 모델이 없거나, 피처 이름·행렬 폭이 다르거나, 예측이 실패하면 그 요청은 휴리스틱 점수를 쓴다.
   레지스트리 확인과 모델 로드는 백그라운드 스레드가 하므로 요청은 기다리지 않는다.
3. 학습 모델을 바로 켜기 - 기각. 서빙 피처와 학습 피처가 같다는 검증(parity)이 먼저다.

### 4. 다양성
`CategoryBasedMMRReranker`(성승우 구현)를 그대로 쓴다. 배치 경로와 요청 경로가 같은 규칙(선호 카테고리
1~2개 λ=0.8, 3~4개 0.7, 5개 이상 0.6, 후보 풀 = top_k x 4)을 쓴다. 요청마다 도는 경로라 탐욕 선택의
이중 파이썬 루프가 가장 큰 프로세스 내 비용이었고, 누적 최대 유사도 벡터로 바꿨다(증거 5).

### 5. 신규 사용자 (콜드스타트 체인)
장기 벡터가 없으면 순서대로: 온보딩에서 고른 뉴스레터의 평균 벡터 -> 선호 카테고리의 최근 뉴스레터
중심 -> 둘 다 없으면 인기 목록. `X-Rec-Source`가 `cold_start_onboarding` / `cold_start_category` /
`cold_start_popular`로 구분해 알려 준다.

### 6. 시간 예산과 폴백
1. 예산 없이 끝까지 계산 - DB가 느려지면 요청 스레드가 전부 묶인다.
2. **시간 예산 300ms + 폴백 체인 (채택)**: 실시간 계산은 작업 스레드(기본 8개)에서 돌고 요청 스레드는
   예산만큼만 기다린다. 초과·예외·빈 결과면 요청 세션으로 `36시간 안의 배치 행 -> 인기 -> 최신` 순서로
   내려간다. 실시간 세션에는 트랜잭션 로컬 `statement_timeout`(=예산)을 걸어, 요청이 이미 폴백으로
   응답한 뒤 남은 작업 스레드가 커넥션을 오래 쥐지 않게 한다. 폴백 결과는 캐시하지 않는다.
   - 폴백 단계는 요청 세션 하나를 같이 쓴다. PostgreSQL은 문장 하나가 실패하면 트랜잭션을 중단 상태로
     두므로, 단계가 실패하면 `rollback`한 뒤 다음 단계로 간다.
   - 표시 단계(`hydrate_today_news`)는 카테고리 매핑이 없는 뉴스레터를 뺀다. 그래서 저장소의 아이템
     조회·인기·최신 목록과 배치 행 필터가 같은 조건(매핑 있음)을 건다. 추천 ID가 비어 있지 않으면 응답
     본문도 비어 있지 않다.

**예산이 묶는 범위는 실시간 계산뿐이다.** 폴백 조회와 표시 단계는 예산이 끝난 뒤 요청 세션에서 돌고,
그 세션에는 `statement_timeout`이 없다. DB 전체가 느린 상황에서는 응답이 300ms를 넘는다.

### 7. 커넥션 풀
요청은 앱 풀 커넥션을 쥔 채 작업 스레드의 결과를 기다린다. 작업 스레드가 같은 풀에서 커넥션을 또 빌리면
동시 요청 수가 풀 크기에 닿는 순간 "요청은 커넥션을 쥐고 작업 스레드는 커넥션을 기다리는" 순환 대기가 된다.
1. 풀 공유(처음 구현) - 16 클라이언트에서 9라운드 중 2라운드가 응답의 94%를 폴백으로 내는 상태에
   빠졌다(증거 3). 이 문제를 처음 본 것은 뉴스레터 3천 개 축소 규모 + 예산 5000ms의 로컬 스모크 실행에서
   16 클라이언트가 QueuePool 30초 타임아웃 에러로 끝났을 때다. 그 실행은 노트북 loadavg가 150을 넘던
   때라 수치는 버렸고, 메커니즘만 통합 테스트(앱 풀을 요청 세션이 전부 쥔 상태)로 남겼다. 운영 예산
   300ms에서는 에러가 아니라 예산 초과 폴백으로 나타난다.
2. 앱 풀을 키우기 - 순환 대기의 문턱만 옮긴다.
3. **실시간 경로 전용 풀 (채택)**: 작업 스레드 수와 같은 크기, `max_overflow=0`, `pool_timeout`=예산.
   작업 스레드는 풀을 기다리지 않는다. **대가가 있다**: 32 클라이언트에서 전용 풀 쪽 p50이 세 실행 모두
   공유 풀의 1.5~1.8배다(증거 3). 이 결정의 근거는 속도가 아니라 순환 대기를 없애는 것이다.
4. 모델 레지스트리 확인과 노출 로그 쓰기는 작은 **보조 풀**(1+1)을 쓴다. 그래서 요청 하나가 앱 풀에서
   쓰는 커넥션은 요청 세션 1개뿐이고, 응답 뒤 작업과 요청 세션 정리의 순서(FastAPI 버전에 따라 다르다)에
   기대지 않는다.

### 8. 캐시
- 추천 결과: 프로세스 안 TTL 60초, 키 `(user_id, last_click_id)`. 클릭이 들어오면 키가 바뀌므로 워커가
  여러 개여도 무효화 신호 없이 다음 요청이 새로 계산된다. 대가는 캐시가 적중해도 요청마다
  `last_click_id` 조회 한 번(0.24~0.36ms)이 든다는 것이다.
- 아이템(임베딩·생성 시각·기사 수): 프로세스 안 TTL 1시간. 생성 뒤 바뀌지 않는 값이다. 벡터 300개를
  DB에서 받아 푸는 비용(10.7~16.9ms, 증거 3)을 프로세스당 한 번만 낸다.
- Redis 공유 캐시 - 기각. 워커별 캐시의 손해는 워커 수만큼의 중복 계산뿐이고, 상시 구성요소 하나를
  더 두는 비용이 그보다 크다.

### 9. 노출 로그
응답으로 실제 내보낸 항목만 `recommendation_impression_log`에 응답 뒤(BackgroundTasks) 기록한다.
- `position`: 화면 응답(표시 단계를 거친 목록) 안의 **0부터 시작하는** 순위.
- `score`: `realtime`·`cold_start_onboarding`·`cold_start_category`는 MMR 재정렬 **전**의 관련도 점수,
  `cold_start_popular`는 인기도-최신성 점수, `batch`·`popular`·`recent` 폴백은 NULL.
- `source`, `model_version`: 응답 헤더 `X-Rec-Source`, `X-Model-Version`과 같은 값.
- `propensity`(NULL), `explored`(false): 탐색 슬롯을 넣을 때 쓸 자리만 잡아 뒀다.

**지금 정책은 결정적이다.** 탐색이 없으므로 이 로그로 IPS/SNIPS 같은 off-policy 추정은 할 수 없다.
쓸 수 있는 것은 순위·출처·모델 버전별 on-policy 클릭률뿐이고, 그마저도 "결과와 한계"의 제약이 붙는다.

### 10. API 이미지
API 이미지는 `backend/app`만 담는 슬림 이미지다(ADR 0006).
1. `backend/requirements.txt`에 `-e ../ai_workspace/recommend_engine` - 기각. 이미지 빌드가 깨지고
   pandas/scikit-learn/lightgbm이 딸려 온다.
2. MMR을 `backend/app`에 복사 - 기각. 같은 알고리즘이 두 벌이 된다.
3. **`recommend_engine`의 `src/core`(numpy만 임포트)만 이미지에 복사 (채택)**. 인기 점수 식은 DB 엔진을
   끌어오지 않는 `app/recsys/popularity.py`로 옮기고 배치 랭킹이 거기서 임포트한다.

이미지에 lightgbm은 넣지 않았다. 따라서 **지금 이미지에서는 LightGBM 스코어러를 켤 수 없다**(켜도 로드
실패로 세고 휴리스틱을 쓴다). 피처 함수 모듈과 lightgbm을 이미지에 넣는 일은 학습 모델을 켜는 변경에서 한다.

## 결정
- `backend/app/recsys/` 패키지가 `GET /newsletters/today`를 요청 시점에 계산한다. 응답 본문 형식은
  그대로이고 헤더 `X-Rec-Source`, `X-Model-Version`, `X-Request-Id`가 붙는다.
- 설정은 `RECSYS_*` 환경변수(`app/recsys/config.py`)다. `RECSYS_MODE=realtime|batch`, 예산 300ms,
  top_k 20, 신선도 창 72시간, 단기 벡터는 최근 24시간의 최근 20클릭 평균(ADR 0017), 배치 행 유효 36시간,
  작업 스레드 8. 설정 오류는 앱 기동(lifespan)에서 실패한다.
- 풀은 셋이다: 앱 풀(요청 세션), 실시간 전용 풀(작업 스레드 수), 보조 풀(레지스트리·노출 로그).
- Alembic 리비전 `8b7f830013b7`(부모 `d48994e9d26e`, head 하나): `recommendation_impression_log`,
  `model_registry`, 요청 경로 인덱스 5개(`news_letter(created_at DESC)`, `news_letter_today_batch(user_id,
  created_at DESC)`, `news_letter_categories(news_letter_id)`, `user_preferred_newsletter(user_id)`,
  `user_preferred_categories(user_id)`).
- `GET /recsys/stats`(로그인 필요)는 살아 있는 프로세스의 카운터를 보여 준다. 기간별 출처 분포는
  `jobs.run daily_report`가 노출 로그에서 센다.
- `jobs.run user_embed`는 최근 24시간에 클릭한 사용자의 장기 벡터를 다시 계산한다(잡 자체는 아직 꺼져 있다).

## 증거

모든 로컬 수치는 Apple M2 노트북에서 `nice -n 19`, BLAS 2스레드로 쟀고 그때의 loadavg를 함께 적는다.
CI 수치는 GitHub 호스티드 러너(x86_64, 4 vCPU, Ubuntu 24.04)의 값이다. 결과 원본은 `reports/serving/`에 있다.

### 1. 단위 테스트
`tests/recsys/` 54건(메모리 fake 저장소, benchmark 2건 제외)과 `tests/recommend_engine/
test_mmr_vectorized_equivalence.py` 15건. CI 실행 37350694153(커밋 `b66dd99`)에서 전체 단위 테스트

1. **전용 풀은 더 빠르지 않다.** 32 클라이언트에서 전용 풀의 p50은 세 실행 모두 공유 풀의 1.5~1.8배
   (175~176 대 98~115, 143~145 대 79~89, 187~189 대 114~121ms)이고 처리량도 같거나 낮다. 16 클라이언트는
   실행마다 다르다(R1·R2는 대부분의 라운드에서 전용 풀이 느리고 R3은 공유 풀이 느리다). 전용 풀을 택한
   근거는 **견고함**이다:
   공유 풀은 16 클라이언트 9라운드 중 2라운드에서 응답의 94%(375/400, 374/400)가 폴백이 되고 p50이 예산과
   같은 302~304ms가 되는 상태에 빠졌고, 빠지지 않은 라운드에서도 5~7건(1.3~1.8%)이 폴백했다. 전용 풀은
   9라운드에서 0~3건(0~0.8%)이었다. 전용 풀이 왜 더 느린지는 **재지 않았다**(가설: 작업 스레드 8개가
   동시에 numpy·파싱을 돌려 GIL 경합이 늘어난다).
2. **처리량은 4 클라이언트에서 정점이고 그 뒤로 떨어진다.** 97~141 rps(4 클라이언트)에서 76~106 rps
   (8 이상)로 내려간다. 16~32 클라이언트의 p95는 185~253ms로 예산 300ms까지 16~38% 남는다. 가장 느렸던
   R3에서는 p95 244~253ms(여유 16~19%), 16 클라이언트 p99가 283~300ms로 **예산에 닿았다**. 러너는
   4 vCPU이고 배포 대상은 2 OCPU arm64다. 대상 장비에서는 이 여유가 없을 수 있다.
3. **이 측정은 HTTP 수준이 아니다.** `service.recommend`를 직접 부른다. HTTP 파싱, JWT 검증, 표시 단계,
   JSON 직렬화, 노출 로그 쓰기가 없고, 부하를 만드는 스레드와 PostgreSQL이 같은 러너에서 CPU를 나눠 쓴다.
   결과 캐시를 껐으므로(`cache_ttl_s=0`) 캐시가 적중하는 실제 트래픽보다 비관적이고, 빠진 단계가 있어
   실제 요청보다 낙관적이다. 어느 쪽이 큰지는 모른다.
4. **300ms 예산은 실시간 계산만 묶는다.** 폴백 조회와 표시 단계는 그 뒤에 요청 세션에서 돌고
   `statement_timeout`이 없다(대안 6).
5. **32 클라이언트의 p99는 두 배선 모두 2.7~7.2초다**(전용 풀 3.8~5.0초, 위 표에는 없는 꼬리).
   요청 스레드 32개가 앱 풀 15개(5+10)를 나눠 쓰면서 일부 요청이 요청 세션용 커넥션을 초 단위로 기다린다
   (에러는 0건, 벤치마크의 풀 대기 한도는 10초이고 운영 기본값은 30초). FastAPI 동기 엔드포인트의 스레드
   풀 기본값은 40이라 운영에서도 같은 일이 생길 수 있다. 이 ADR은 앱 풀 크기를 바꾸지 않았다.

첫 요청(아이템 캐시가 빈 상태)은 45~76ms였다.

### 4. 휴리스틱 가중치 민감도 (합성, 로컬)
`python -m evaluation.serving.click_shift_sensitivity`. 주제 4개 x 12개(1024차원) 코퍼스에서 장기 프로필이
주제 0(+0.6·주제 2)인 사용자가 주제 1을 N번 클릭한 뒤 상위 10개 중 주제 1의 비율. 10개 시드의
평균 [최소, 최대]:

| 장기 : 단기 | 클릭 1회 | 클릭 2회 | 클릭 3회 |
|---|---|---|---|
| 0.60 : 0.20 | 0.00 [0.0, 0.0] | 0.00 [0.0, 0.0] | 0.01 [0.0, 0.1] |
| 0.50 : 0.30 | 0.10 [0.1, 0.1] | 0.10 [0.1, 0.1] | 0.10 [0.1, 0.1] |
| **0.45 : 0.35** | 0.15 [0.1, 0.3] | 0.29 [0.2, 0.5] | 0.39 [0.2, 0.6] |
| 0.40 : 0.40 | 0.80 [0.8, 0.8] | 0.80 [0.8, 0.8] | 0.80 [0.8, 0.8] |
| 0.35 : 0.45 | 0.89 [0.8, 0.9] | 0.90 [0.9, 0.9] | 0.90 [0.9, 0.9] |
| 0.30 : 0.50 | 0.90 [0.9, 0.9] | 0.90 [0.9, 0.9] | 0.90 [0.9, 0.9] |

**0.45 : 0.35는 절벽 위에 있다.** 가중치를 0.05 옮기면 반응이 "없음"(0.10 고정)에서 "피드 장악"(0.80 고정)으로
넘어간다. MMR이 후보 풀 안에서 점수를 min-max 정규화하기 때문에 반응이 계단형이다. 그리고 이 값은
**결과를 본 뒤에 골랐다**. 코퍼스는 주제가 거의 직교하는 4개뿐인데 실제 BGE-M3 뉴스 임베딩은 그런 구조가
아니다. 시드 DB 통합 테스트에서는 같은 가중치의 효과가 0.00 -> 0.10에 그쳤다(증거 2). 따라서 이 값은
"반응은 하되 클릭 한 번에 뒤집히지는 않게"라는 의도를 담은 **사전값**일 뿐이고, 튜닝 결과나 추천 품질의
근거로 쓰지 않는다. 실제 임베딩과 실제 클릭에서 다시 정해야 한다.

## 결과와 한계

**얻은 것**
- 신규 사용자가 빈 화면을 받지 않는다(응답 본문 기준, 통합 테스트).
- 클릭이 다음 요청에 반영된다(캐시 키가 바뀌고 단기 벡터가 달라진다).
- 실시간 계산이 실패하거나 느려도 요청은 폴백으로 응답하고, 어떤 경로로 응답했는지 헤더와 로그에 남는다.

**확인하지 않은 것 / 재실행 대기(클라우드)**
- 배포 대상에서의 지연. Oracle A1(arm64 2 OCPU)이 확보되면 아래를 돌려 증거 3의 표에 행을 더한다.
  ```bash
  python -m evaluation.serving.request_path_bench \
    --server-url postgresql://<user>:<password>@<host>:5432/postgres \
    --redis-url redis://<host>:6379/0 --out recsys-bench.json
  ```
- HTTP 수준의 지연(JWT·표시·JSON·노출 로그 포함)과 폴백률. 이 저장소에는 아직 HTTP 부하 도구가 없다.
  사용자 시뮬레이터 브랜치(`feat/user-simulator-loadtest`)의 Locust 하네스(`python -m sim.loadtest`)가
  들어온 뒤 API 서버를 띄울 수 있는 환경에서 잰다. 노트북에서는 서버와 부하 테스트를 돌리지 않는다.
- 추천 품질. 오프라인 평가는 ADR 0007의 프로토콜과 ADR 0013의 랭커에서 다룬다. 이 ADR의 어떤 수치도
  "추천이 좋아졌다"는 근거가 아니다.

**알고 있는 한계**
- 휴리스틱 가중치는 합성 코퍼스의 사전값이고 절벽 위에 있다(증거 4). 실제 임베딩에서 다시 정하는 일이 남았다.
- "인기"는 최신성 + 클러스터 크기다. 클릭 인기도가 아니다.
- 노출 로그로 할 수 없는 것:
  - 정책이 결정적이라 IPS/SNIPS 추정을 할 수 없다. `propensity`·`explored`는 자리만 있다.
  - 클릭 로그에 `request_id`와 순위가 없어 클릭과 노출은 (사용자, 뉴스레터, 시각)으로 근사 조인만 된다.
  - 결과 캐시가 적중하면 같은 목록이 새 `request_id`로 다시 기록된다. 캐시 적중 여부와 폴백 사유는
    저장하지 않는다.
  - 쓰기는 응답 뒤의 best-effort다. 실패는 프로세스 카운터(`impressions.failed`)에만 남아 유실률을
    사후에 계산할 수 없다. `daily_report`의 출처 분포는 쓰기에 성공한 응답만 센다.
- `/recsys/stats`의 카운터는 프로세스별이고 재시작하면 0이 된다.
- 결과 캐시와 아이템 캐시는 워커별이다. 워커 수만큼 같은 계산을 한다.
- 타임스탬프는 `timestamp without time zone` 컬럼에 서버 TimeZone 벽시계로 들어 있다. 읽을 때
  `::timestamptz`로 해석하므로 모든 세션의 TimeZone이 같다는 전제에 기대고 있다.
- 폴백 조회와 표시 단계에는 시간 제한이 없다. 앱 풀(15)보다 동시 요청이 많으면 요청 세션 대기가 초 단위가
  된다(증거 3의 5번).
- LightGBM 스코어러는 API 이미지에 lightgbm과 피처 함수가 없어 켤 수 없다. 켜기 전에 서빙 피처와 학습
  피처의 일치 검증이 필요하다.
- `user_embed` 잡이 crontab에서 꺼져 있는 동안 장기 벡터는 갱신되지 않는다. 단기 벡터(ADR 0017)만 클릭을
  따라간다.
- 배치 폴백 단계는 배치 추천 잡이 꺼져 있는 동안 대부분 빈손으로 지나간다(행이 없거나 36시간을 넘긴다).

**후속 작업**
- 노출·클릭 로그 v2(클릭에 `request_id`·순위, 캐시 적중·폴백 사유 저장)와 탐색 슬롯.
- 실제 임베딩·클릭으로 가중치 재도출, 클릭 기반 인기도.
- 앱 풀 크기와 요청 스레드 수의 관계 정리, 요청 세션의 문장 타임아웃.
- 대상 장비·HTTP 수준 측정(위 재실행 대기).
