# ADR 0026: 호스팅 계층과 비상 계획 — Always Free만으로 (개발 Mac · Tier 0 E2.1.Micro · Tier 1 A1)

## 상태
채택됨 (2026-09-26). 같은 날 17:00 KST에 전제가 바뀌어 결정 2를 갱신했다 — 사용자 요청으로 Mac 수집 스택을
내렸고, A1이 확보될 때까지 **Tier 0가 유일한 수집기**다(승격 조건 3을 통과하지 않은 상태에서의 결정이며, 위험은
결과와 한계에 적었다). Tier 1(A1)은 용량 부족으로 아직 확보하지 못했다 — 확보되면 결정 4의 측정 결과로 이 ADR을
갱신한다. 증거는 같은 날 22:18 KST까지의 관측으로 갱신했다. 운영 절차는 [runbook-hosting.md](../runbook-hosting.md).

**2026-10-06 갱신.** Tier 0 단독 수집이 10일째다(증거 8, 04:41 KST 조회). VM은 회수되지 않았고 `news_raw`는
14,230행이 됐다. A1은 여전히 없다. 승격 조건(결정 3)은 통과하지 못했다 — 호스트 밖 백업이 09-26 22:18 이후
한 번도 없어 그 뒤 수집한 13,435행이 VM 한 곳에만 있고, 정시 ingest 233회 중 27회는 앞 회차가 1시간을 넘겨
시작되지 않았다. 결정 6의 재검토 조건(단독 수집 7일 초과 + 백업 자동화 없음)에 해당한다. 무엇을 할지는 이
갱신에서 정하지 않았다(결정 6 끝, 사용자 결정 대기). 아래 본문에서 날짜 없이 "지금"이라고 쓴 곳은 2026-09-26
22:18 KST 기준이다.

**2026-10-17 갱신.** VM의 코드를 09-26 스냅숏에서 `13801fc`(본문 보존 잡 ADR 0023, 발행 시각 KST 수정 ADR 0008,
정책브리핑 수집 코드)로 다시 배포했다(증거 9, 런북 4.1). 배포 직전에 호스트 밖 백업을 떴다(`news_raw` 30,754행).
되돌릴 일은 없었다. A1은 여전히 없고 승격 조건(결정 3)도 그대로 통과하지 못한 상태다.

**2026-10-17 갱신 2.** 동아일보 본문 다운로드 실패의 원인을 읽기 전용으로 진단했다(증거 10): 동아일보 서버가 VM에서 온

시작부터 잰 추출 마감·RSS 소켓 상한·언론사별 건전성 검사와 RSS 피드별 경고)를 코드로 넣었고 **Tier 0에는 배포하지 않았다** —
효과는 아직 계산이지 측정이 아니다.

**2026-10-17 갱신 3.** 결정 6의 재검토를 닫았다 — 선택지 (2) "백업을 Mac이 아닌 곳에서 자동화"를 택했다. VM 호스트의 cron이

검증도 한 번 했다. 유휴 지표도 같은 cron이 VM에서 매일 잰다. 승격 조건 (b)의 장치는 갖췄지만 "매일"은 스케줄 실행을 며칠 본 뒤에
판단한다 — 승격은 하지 않았다.

**2026-10-18 갱신(배포).** 같은 날 06:29~06:32 UTC에 런북 4.1 절차로 Tier 0을 main `e9864cf`로 재배포했다 - 결정 9 코드(요청 상한·언론사별 차단기·추출 마감·RSS 소켓 상한), 새 `daily_report` 줄, 백업 스크립트의 main 판(cron `TIER0_BACKUP_GIT_SHA`도 같은 SHA). ## 컨텍스트
- **예산: 호스팅 비용 $0.** 유료 전환(PAYG 포함)은 하지 않는다(사용자 결정). LLM API 비용은 이 ADR 범위 밖이다.
- **기존 운영:** Mac(Apple M2 16 GB, colima) 위의 compose 스택이 매시 수집하고(기록 시스템), BGE-M3 임베딩은
  호스트 MPS(launchd)로 돌았다(ADR 0006). 노트북은 잠자기·재부팅·이동 때문에 수개월 상시 운영이 불가능하고,
  평가셋에 필요한 5~7일 연속 수집의 단일 장애점이다(2026-09-26 아키텍처 리뷰 D2). 실제로 2026-09-26
  12:53~16:50 KST에 colima VM이 멈춰 Mac 수집이 4시간 끊겼다(증거 6).
- **2026-09-26 17:00 KST, Mac 스택 중단:** 노트북 응답성을 지키려고 사용자가 로컬 서버를 모두 내리게 했다(colima·
  compose·launchd 임베더). 직전 상태는 `pg_dump -Fc` 덤프(16:59 KST, `news_raw` 899행)로 저장소 밖에 보관했다.
- **OCI 테넌시(2026-09-26 CLI 확인):** 홈 리전 ap-tokyo-1, 가용 도메인 1개. 구독 `plan-type=FREE_TIER`,
  `upgrade-state=PROMO`(체험 기간), `is-intent-to-pay=false` — PAYG가 아니다.
- **A1은 확보되지 않는다:** 2026-09-26 00:40~22:18 KST에 A1.Flex 생성 791회 시도 — "Out of host capacity" 418회,
  "Too many requests"(429) 373회, 성공 0회, 한도 초과(LimitExceeded) 0회. 요청 자체는 한도 안이고 용량만 없다.
  재시도 루프는 Mac에서 돌기 때문에 Mac이 멈춘 12:52~16:43 KST에는 시도가 없었다. 루프는 계속 돈다.
  2026-10-06 04:43 KST까지 누적 4,215회 — 용량 부족 2,166회, 429 2,029회, 엔드포인트 시간 초과 20회, 성공 0회,
  한도 초과 0회. 루프가 09-28 18:02에 죽은 것을 10-06 02:03에야 다시 띄워서 그 사이 약 7.3일은 시도가 없었다.
- **공식 Always Free 조건**(docs.oracle.com "Always Free Resources", 2026-09-26 조회):
  E2.1.Micro는 테넌시당 2대, 1/8 OCPU(추가 CPU를 쓸 수 있음), 메모리 1 GB, 인터넷 50 Mbps.
  A1은 월 1,500 OCPU-시간·9,000 GB-시간(상시 2 OCPU/12 GB 상당). 부트+블록 볼륨 합계 200 GB.
  Always Free 컴퓨트는 홈 리전에서만 만들 수 있고, "out of host capacity"는 일시적인 셰이프 부족이다.
- **유휴 회수 규칙**(같은 문서): "Idle Always Free compute instances may be reclaimed by Oracle."
  7일 동안 다음이 **모두** 참이면 유휴로 본다 — CPU 사용률 95번째 백분위 < 20%, 네트워크 사용률 < 20%,
  메모리 사용률 < 20%(A1 셰이프만). 집계 해상도, 네트워크 사용률의 분모, 회수가 정지인지 삭제인지,
  사전 통지 여부는 문서에 없다.
- **임베딩 메모리:** BGE-M3 fp32 로드에만 익명 메모리 3.6 GB가 필요하다(ADR 0006 증거 5). 1 GB 호스트에서는
  임베딩을 돌릴 수 없다.

## 검토한 대안

### 1. 어디서 상시 운영할 것인가
1. **PAYG 전환 후 A1** — A1 용량 우선 배정·유휴 회수 제외가 커뮤니티에서 보고되지만 공식 문서로는 확인하지
   못했다. 결제 수단 등록과 소액 과금 위험. 예산 원칙 위반 → 기각.
2. **A1만 기다린다** — 확보 시점을 알 수 없다(위 재시도 통계). 기다리는 동안 Mac이 단일 장애점으로 남는다 →
   단독으로는 기각, Tier 1로 유지.
3. **Mac만** — MPS 임베딩·LLM 생성·평가에는 가장 빠르지만 24/7이 아니다(증거 6의 4시간 공백) → 개발 계층으로 한정.
4. **E2.1.Micro(1 GB) Tier 0** — 무엇이 들어가는지 실측해서 범위를 정한다 → **채택(수집 데이터 플레인만).**
5. **GitHub Actions 배치 + 외부 DB(리뷰 3.3 B안)** — 무료 러너 조건(공개 저장소), 60일 무커밋 시 cron 비활성,
   러너에서 DB로 가는 터널, 수집 본문이 러너를 거치는 문제. Tier 0 VM이 같은 역할을 더 단순하게 한다 → 보류.
6. **유료 최소 VPS(리뷰 Tier 2)** — 예산 원칙 위반 → 기각(예산 원칙이 바뀌면 재검토).

### 2. Tier 0에서 무엇을 돌릴 것인가
1. 전체 compose(worker 이미지, embed 포함) — worker 이미지에 CPU torch·BGE-M3가 들어 있고 임베딩은 3.6 GB가
   필요하다 → 기각.
2. **수집(rss·extract)·popularity·daily_report만, 전용 슬림 이미지** — 채택. torch·hdbscan·lightgbm·LLM SDK를 뺀
   `docker/ingest.Dockerfile`(의존성은 worker 잠금 파일을 제약으로 걸어 같은 버전)과 `docker/crontab.micro`.
3. 추출 워커 수: 기본 8개(ProdSettings)는 1 GB에서 돌려 보지 않았다. 2개로 빈 DB 첫 ingest(431건)가 추출 132초,
   잡 컨테이너 최대 258 MiB였고(증거 2·3) 매시 신규는 16~60건이라 2개로 충분하다 → 2개로 고정.

### 3. 방화벽
1. **UFW로 22만 허용** — 처음 계획. 그러나 OCI 공식 문서(Compute Best Practices, "Essential Firewall Rules")가
   "Do not use Uncomplicated Firewall (UFW) to edit firewall rules on an Ubuntu image"라고, UFW로 규칙을 고치면
   인스턴스가 부팅되지 않을 수 있다고 경고한다(iSCSI 부트 볼륨용 필수 규칙이 iptables에 있음) → 기각.
   VM에는 `ufw` 패키지가 설치돼 있지 않다(의도).
2. **OCI 이미지 iptables 유지 + IPv6 보강** — 이미지 기본 IPv4 규칙이 이미 "22/tcp 신규 연결만 허용, 나머지
   REJECT"다. 확인만 하고 비어 있던 IPv6 규칙을 같은 정책으로 채운다 → 채택. 목적(인바운드 22만)은 같고,
   실제 상태는 증거 5에 있다.

### 4. 유휴 회수 대응
1. **인위적 CPU 부하**(busy loop·lookbusy류로 p95를 20% 위로) — 효과는 확실하지만 규칙의 취지(쓰지 않는 자원
   회수)를 우회하고, 1/8 OCPU 버스트 자원을 수집 잡과 나눠 쓴다 → 기본 미채택.
2. **회수돼도 잃는 것이 없게 운영 + 조기 경보 + 빠른 재생성** → 채택(결정 6).

### 5. A1로 옮길 때 두 DB를 어떻게 합칠 것인가
1. **Tier 0 DB만 옮긴다** — 11:36 KST 이전 Mac 수집분(690행)과 임베딩 845개를 잃는다 → 기각.
2. **Mac 덤프만 복원한다** — 17:00 KST 이후는 Tier 0에만 있다 → 기각.
3. **Mac 덤프 복원 + Tier 0 행을 URL로 병합** — 두 DB의 `raw_news_id`·`press_id`는 서로 다르므로 id가 아니라
   `raw_news_url`(UNIQUE)로 합치고 언론사는 이름으로 매핑한다. 본문 해시가 이미 있는 행은 `duplicate`로 넣는다
   (부분 UNIQUE `uq_news_raw_content_sha256_ok`) → 채택(결정 4, 런북 6.4).

   | 반출 금지 데이터(EB-NeRD 등) | O (Mac 전용) | X | X |

2. **기록 시스템(갱신)** — 11:36 KST까지는 Mac, 11:36~17:00 KST는 두 곳에 겹쳐 있고, 17:00 KST 이후는 Tier 0에만
   있다. 즉 지금의 기록 시스템은 "Mac 덤프(동결, 899행) + Tier 0 DB"의 합집합이다. Tier 0는 승격 조건(결정 3)을
   통과하지 않은 채 유일한 수집기가 됐으므로 "운영 중"이 아니라 **"임시 단독 수집"**이라고 부른다.
   이 기간 Tier 0 DB의 호스트 밖 백업은 Mac이 SSH로 당겨 오는 `pg_dump -Fc`(런북 6.5)이고, 자동화는
   Mac에서 상주 작업을 돌리지 않기로 한 동안 보류다 — 백업 간격만큼이 회수·장애 시 최대 손실이다.
   **2026-10-17부터**는 VM 호스트의 cron이 매일 OCI Object Storage로 올린다(결정 6의 2026-10-17 결정, 증거 11). 최대 손실은
   하루치 수집분(약 1,300행)이고, 본문은 최근 27일 수집분까지만 되살릴 수 있다(ADR 0023 개정 2026-10-17 2).

     결국 성공하던 기사 요청을 끊는지는 **재지 않았다** — 예전 코드는 요청 시간을 남기지 않았고, 같은 서버의 RSS는 VM에서
     성공해도 30~321초·첫 바이트 최대 74초였다(증거 10 c). 그래서 성공한 요청의 시간 구간을 남기고, 배포 뒤 `>=15s` 구간과
     `read_timeout`·`deadline` 비율을 함께 본다 — `ok`가 줄었을 때 차단 때문인지 상한 때문인지 가르는 값이다. RSS에는 같은
     상한을 넣지 않았다(같은 상한이면 그런 느린 성공이 실패로 바뀐다). 대신 요청 전체가 아니라 소켓 대기 1번(연결·읽기
     각각)에 120초 상한(`RSS_SOCKET_TIMEOUT_S`)만 둔다 — 예전에는 feedparser가 urllib을 시간 제한 없이 불러, 붙잡는 RSS
     서버에 ingest가 끝없이 멈출 수 있었다. 대기 1번이 120초를 넘지 않는 느린 성공은 끊지 않는다(대기 1번의 최대값은 재지
     않았다 — 첫 바이트까지가 최대 74초였다).
   - 언론사별 차단기: 한 실행 안에서 같은 언론사 기사가 연달아 3건 **사이트 단위 원인**(연결·읽기 실패, 5xx, 403·408·425·429)으로
     다운로드에 실패하면, 그 언론사의 남은 기사는 이번 실행에서 보내지 않는다(`extract.press_breaker`·`deferred`). 없는 기사
     (404·410 같은 4xx), 크기·리다이렉트 상한, 분류 밖 예외는 그 기사만의 문제라 세지도 0으로 되돌리지도 않는다 — 대상이
     `ORDER BY raw_news_id`라 앞서 실패한 죽은 URL이 언론사마다 회차 맨 앞에 오는데, 그것 3건으로 건강한 언론사의 새 기사를
     미루면 안 된다. 미룬 기사는 DB에 쓰지 않으므로 시도 횟수(상한 3회)를 쓰지 않는다. 예전에는 차단 시간대에 걸린 동아일보
     기사가 회차마다 시도를 하나씩 써서 세 회차 뒤 영구 실패가 됐다(10-16 수집분 280건 중 103건). 거부가 이어지면 회차마다
     가장 오래된 3~4건만 시험 삼아 받으므로, 그런 회차에서 동아일보로 가는 실패 요청은 10번 안팎이다(예전: 7일 약 2만 번 =
     실패 2,288건 x 요청 9번). 거부와 통과가 섞이는 회차에서는 차단기가 늦게 열리거나 열리지 않아 요청이 더 많다. 기준 3건은
     증거 10 (f)로 확인했다: 같은 회차에서 3건 연속 실패 뒤 다음 기사의 다운로드 성공 비율은 0.25로, 바로 앞이 성공일 때(0.86)보다
     훨씬 낮다 — 나쁜 구간을 골라 미룬다. 대신 회차당 동아일보 처리량을 묶어(예전 순서에 대 보면 회차당 9.4건), 새 기사와
     재시도를 합친 수요를 따라가지 못하면 미시도 기사가 쌓일 수 있다(같은 증거). 배포 뒤 미시도 잔량으로 본다.
   - 시도 순서: 대상은 지금처럼 `ORDER BY raw_news_id`(오래된 것부터)다. 그래서 차단기가 열리는 회차의 시험 요청 3~4건은
     매번 앞서 실패한 재시도 기사에 가고, 거부가 이어지는 동안 새 기사는 그 재시도들이 시도 상한을 다 쓸 때까지 뒤로 밀린다 —
     뉴스레터에는 새 기사의 신선도가 중요하다. 규칙은 바꾸지 않았다. 미시도 잔량이 늘 때 고를 대안으로 적어 둔다: 언론사 안에서
     시도한 적 없는 기사를 재시도보다 먼저 보내는 정렬(`ORDER BY (raw_news_extract_status IS NOT NULL), raw_news_id`). 그러면
     거부 중에는 새 기사가 시험 요청을 맞아 시도를 하나씩 쓰고, 앞서 실패한 기사는 거부가 풀린 회차에만 다시 시도된다.
   - 실행 시간 마감: crontab의 `ingest --extract-deadline-s 2700`. ingest 시작 뒤 45분(:50)이 지나면 새 기사를 보내지 않고
     남은 기사를 다음 회차로 미룬다(시도 횟수를 쓰지 않음). 마감은 추출 시작이 아니라 **ingest 시작부터** 잰다 — RSS 단계가
     늦을수록 추출 시간이 준다(최소 60초). 그래서 :05에 시작한 회차는 :50 + 이미 보낸 기사의 요청 상한 62초(소켓 제한이 적용될
     때, DNS 조회 제외)와 그 기사의 본문 추출·DB 쓰기 안에 끝난다 — RSS 단계가 :50 전에 끝나는 한. RSS 단계 전체에는 상한이
     없다: 피드 하나가 응답 대기나 본문 도중에 붙잡히면 120초 한 번(재시도 없음), 연결·TLS 단계에서 붙잡히면 120초 x 3번 + 대기
     3초(약 6분)다. 피드 10개가 한꺼번에 연결 단계에서 붙잡히거나, 대기 1번을 120초 안으로 이어 가며 조금씩 흘려보내는 RSS
     서버가 있으면 :50을 넘길 수 있다(관측된 적 없음 — RSS 단계 관측 최대 321초). 추출에 남는 시간(RSS 321초를 빼도 약 40분)은
     실패가 없는 회차의 추출 최대(374초, 증거 10 b)의 6배가 넘는다.
   - 건전성 검사(ADR 0006 결정 9의 실패 조건을 바꾼다): 한 언론사만의 실패는 원인 개수·미룬 건수와 함께 경고하고 실행은
     성공시킨다. 실행을 실패시키는 것은 건강하지 않은 언론사(차단기가 열렸거나, 받은 기사 3건 이상 중 절반 이상 실패)가
     두 곳 이상일 때, 또는 가장 많이 실패한 언론사를 빼고도 받은 기사 5건 이상 중 절반 이상이 실패했을 때다. 미룬 기사는
     받지 않았으므로 분모에 넣지 않는다. 여기서는 404 같은 기사 단위 실패도 실패로 센다 — 사이트 전체의 기사 주소 체계가
     바뀌면(전부 404) 차단기는 열리지 않아도 경고는 나야 하기 때문이다. RSS 단계에서 읽지 못한 피드도 피드마다 경고한다
     (`동아일보: RSS 수집 실패 (RemoteDisconnected) - 이번 회차 신규 기사 0건`) — 그 회차에 그 언론사의 추출 대상이 없으면
     추출 경고가 나지 않아, 이것이 없으면 수집량 0이 알림 없이 지나간다(10-16 22:05 ~ 10-17 05:05 UTC 8회 중 7회 동아일보 RSS
     실패, 그중 추출 대상에 동아일보가 없던 4회는 경고 0건). 모든 피드가 실패하면 지금처럼 실행을 실패시킨다. 이 바꿈만으로
     "끝난 잡 성공률"(결정 3 a)은 수집이 나아지지 않아도 오른다 — 결정 3을 다시 볼 때는 규칙을 바꾼 커밋 앞뒤
     (`job_runs.git_sha`)를 나누고, 언론사별 `fetch_failed`·미룬 건수와 정시 회차 수를 함께 적는다.
   - 하지 않은 것: User-Agent 바꾸기, 프록시, 다른 주소(모바일·AMP 페이지)로 우회. 사이트가 출발지를 보고 거부하는 것을
     피해 가는 일이라 하지 않는다(증거 10 c에서 브라우저 User-Agent도 똑같이 거부됐다). 동아일보를 어디서 얼마나 수집할지
     (지금처럼 VM에서 받을 수 있는 만큼 / 클라우드가 아닌 곳에서 동아일보만 / Tier 0 피드에서 빼기)는 정하지 않았다(사용자
     결정 대기).
     범위 종결 C-31 (2026-10-18): 유보 - 소유자 결정이다. 결정 9를 배포한 뒤의 관측(미시도 잔량, 최종 `fetch_failed` 비율)이 판단 자료다.

  (표본 치우침, 요청 방식 차이, 새 코드에서는 건너뛰는 정시 회차가 줄어 회차 수가 는다). 조회 시점에 아직 시도하지 않은 동아일보
  기사(수집 30일 안)는 0건이다 — 배포 뒤 비교할 기준값이다.

## 결과와 한계
- **비용 $0 유지.** 만든 유료 자원 없음. 셰이프 과금 유형 `ALWAYS_FREE`, 볼륨 합계 150 GB(대기 A1 포함) ≤ 200 GB.
- **1 GB에 수집 데이터 플레인이 들어간다.** 10.5시간 소크에서 MemAvailable 최소 379 MiB(p5 404), 스왑 최대
  105 MiB, OOM 0, 끝난 잡 22/22 성공, 수집 지연 p95 1.5시간. 임베딩·클러스터링·생성은 들어가지 않는다 —
  Tier 0만으로는 뉴스레터를 만들 수 없다.
- **섀도 수집기는 실제로 공백을 메웠다.** Mac이 4시간 멈춘 동안 Mac이 영영 놓친 32건(세계일보)을 Tier 0가 갖고
  있고, 같은 구간 Mac 수집분은 Tier 0가 전부 갖고 있다. 다만 이 수치는 피드 창 크기에 달린 하루치 관측이다.
- **A1 이전 데이터 경로는 리허설을 마쳤다.** Mac 덤프 복원 + Tier 0 URL 병합이 실데이터로 기대 행 수(1,087)와
  정확히 맞았고, 다시 돌려도 바뀌지 않으며(멱등), 검증 실패 시 전부 되돌린다(증거 7).
- **지금 가장 큰 위험: 승격 조건을 통과하지 않은 단독 수집기.** 17:00 KST 이후 수집분은 Tier 0 한 곳에만 있고,
  정상 상태 지표로는 공식 기준상 회수 대상이다(증거 4). 호스트 밖 백업은 수동 `pg_dump` 당겨 오기뿐이며(마지막
  22:18, 795행) 자동화는 보류다 — 회수·디스크 손상 시 마지막 백업 이후를 잃는다. Mac 덤프(899행)도 Mac 디스크에만
  한 부 있다. 이 위험은 노트북 응답성과 맞바꾼 것으로 사용자가 정했다.
- **동아일보 추출이 Tier 0에서 불안정하다.** Mac 899행에는 fetch_failed가 0건인데 Tier 0에서는 10건이 남았고, 그런
  회차는 추출이 20분 넘게 걸렸다. 원인(OCI IP 제한 여부)은 두 수집기를 같은 시간에 돌려 비교해야 가를 수 있다.
- **AI타임스 발행 시각이 수집 시각보다 5~9시간 뒤로 저장된다**(증거 3 — Tier 0 6.2~9.0시간, Mac 덤프
  5.0~8.9시간). 호스팅과 무관한 수집기 결함이지만 수집 지연 지표와 시점 기준(point-in-time) 평가셋의 기사 시각에
  영향을 주므로 따로 고친다.
  **2026-10-06: 수집기 코드는 고쳤다**(시간대 없는 발행 시각을 KST로 읽는다 — ADR 0008 "2026-10-06 갱신").
  남은 것은 둘이고 둘 다 하지 않았다: 고친 코드의 Tier 0 재배포(그 전까지 AI타임스 새 행은 계속 9시간 뒤로
  저장된다), 이미 저장된 행의 보정(SQL 제안은 [runbook-hosting.md](../runbook-hosting.md) 6.7 — 실행하지
  않았고 범위·시점은 사용자 결정 대기).
  범위 종결 C-30 (2026-10-18): 완료 - ADR 0008 "2026-10-17 갱신: 기존 행 보정"(605행 보정, 보정 뒤 발행 > 수집 0행).
- **아직 검증하지 않은 것:** A1(arm64)에서의 승격 절차 전체(용량 없음 — 병합은 x86 Tier 0의 일회용 DB에서만
  리허설), Tier 0 백업의 복원 검증과 자동화, 7일 소크, 유휴 회수의 실제 동작(정지인지 삭제인지).
- **유휴 지표는 근사치다.** 공식 문서가 집계 해상도·네트워크 분모를 밝히지 않아 `idle_check.py`는 1분 평균과
  셰이프 대역폭(50 Mbps)을 가정한다. 경보용이지 판정용이 아니다.
- **증거 6의 시각 표기:** `raw_news_crawled_at`은 시간대 없는 컬럼이고 두 컨테이너 모두 UTC로 기록한다(각 DB의
  `job_runs.started_at`과 대조해 확인).

### 2026-10-06 갱신 (증거 8)
- **1 GB VM이 10일을 버텼다.** 14,230행을 모았고 OOM 0, 유휴 회수 없음, 예약 재부팅 뒤 사람 손 없이 다음 정시
  회차부터 수집을 이어 갔다. 비용은 여전히 $0다(만든 자원은 E2.1.Micro 1대와 부트 볼륨 50 GB뿐).
- **수집 품질은 09-26 하루치보다 나빠졌다.** 정시 회차의 85.0%만 성공했고(233회 중 198회), ingest가 1시간을
  넘겨 다음 회차를 건너뛴 것이 27회다. 실패 8건과 fetch_failed의 99%가 동아일보 쪽이다. "매시 수집"이라고 쓰려면
  이 수치를 같이 적어야 한다.
- **가장 큰 위험은 그대로이고 더 커졌다.** 마지막 호스트 밖 백업(09-26 22:18, 795행) 뒤의 13,435행이 VM 한
  곳에만 있다. 7일 창 지표는 공식 유휴 기준을 채운다. Mac 덤프(899행·임베딩 845개)도 여전히 Mac에 한 부뿐이다.
- **승격 조건의 빈틈을 찾았다.** "끝난 잡 성공률"은 시작되지 않은 회차를 세지 않아 첫 7일이 99.1%로 나온다.
  같은 기간 정시 회차 기준으로는 85.7%다. 기준을 고칠지는 정하지 않았다(결정 3).
- **아직 하지 않은 것(위 목록에 더해):** 10-06 시점 백업과 그 복원 검증, Mac 덤프의 두 번째 사본, 최신 코드의
  Tier 0 재배포(정책브리핑 수집·Alembic `8b7f830013b7`·발행 시각 KST 수정 포함 — 수집 전용 이미지에서 해당
  모듈이 임포트되는 것까지만 확인했고 VM에서 돌려 보지는 않았다), AI타임스 기존 행의 발행 시각 보정(런북 6.7,
  사용자 결정 대기), 동아일보 실패 원인 구분, 재부팅 뒤 메모리 표본 수집 재개, 병합 SQL integration 테스트의
  첫 CI 실행 결과 확인.

### 2026-10-17 갱신 2 (증거 10, 결정 9)
- **동아일보 실패 원인을 갈랐다.** 동아일보 서버가 VM에서 온 요청을 연결 단계에서 거부한다 — 같은 시각 같은 URL·User-Agent로
  Mac은 20/20 성공, VM은 0/20. HTTP 오류·페이지 개편·리다이렉트는 아니다. VM의 IP 하나인지, OCI 대역·일본 출발 전체인지는
  모른다.
- **1시간을 넘기는 회차의 대부분은 우리 쪽 재시도 구조 탓이었다.** 실패 기사 1건이 HTTP 요청 9번과 대기 93초가 돼 워커를
  약 4분 붙잡았고, 추출 시간은 실패 수로 R² 0.96만큼 설명된다. 결정 9로 고쳤지만 **배포하지 않았다** — "1시간 초과 회차가
  없어진다"는 아직 계산(RSS 단계가 :50 전에 끝나면 :51 무렵 종료)이지 측정이 아니다.
- **이 수정으로 동아일보 수집량이 돌아오지는 않고, 줄 수도 있다.** 거부되는 동안은 받을 수 없다. 늘 수 있는 것은 미룬 기사가
  시도를 쓰지 않아 거부가 풀린 뒤에 받을 수 있게 되는 몫이다. 줄 수 있는 쪽도 있다: 기사 1건에 보내는 요청이 9번에서 2번으로
  줄고(그 2번이 읽기 15초·요청 30초 상한에 걸리는 느린 성공도 있을 수 있다 — 재지 않았다), 차단기가 회차당 동아일보 처리량을
  묶는다 — 예전 순서에 대 보면 회차당 9.4건으로 새 기사 유입(약 8.8건)과 비슷하다(증거 10 f). 어느 쪽이 큰지는 배포 뒤에 잰다.
- **배포 뒤 확인할 항목** (결과를 보고 무엇을 정하는 규칙이 아니라 상태 확인이다): 1시간 넘는 ingest 회차 수, 시작되지 않은
  정시 회차 수, 동아일보 최종 `fetch_failed` 비율과 `ok` 건수(수집일 기준, 위 (a)와 같은 식), 아직 시도하지 않은 동아일보
  기사 수와 그중 가장 오래된 것의 나이(미시도 잔량 — 배포 전 0건, 늘어나면 차단기가 처리량을 묶고 있는 것이다. 미룬 기사는
  최종 `fetch_failed`로 세어지지 않으므로 실패 비율만 보면 놓친다), 회차당 동아일보 실패 요청 수, 경고 빈도(RSS 피드별 경고와
  추출 경고를 나눠서), `extract.fetch_fail_causes`의 원인 구성, `extract.fetch_ok_latency`의 `>=15s` 구간과 `read_timeout`·
  `deadline` 비율(함께 늘면 상한이 느린 성공을 끊고 있을 수 있다 — 차단의 `disconnect`·0바이트와 가른다). 확인 쿼리는 런북 6.6.
- **남은 한계:** RSS 단계 전체에는 시간 상한이 없다 — 소켓 대기 1번 120초만 있고, 추출 마감을 ingest 시작부터 재서 RSS가 늦은
  만큼 추출이 줄 뿐이다. 피드 여러 개가 한꺼번에 붙잡히거나 조금씩 흘려보내는 RSS 서버가 있으면 다음 정시 회차와 겹칠 수 있다
  (관측된 적 없음, 결정 9). 동아일보 RSS 실패(418회 중 263회, 10-17 06:11 UTC 기준 423회 중 267회)는 그대로이고, 이제 피드별
  경고로 보인다. VM에 Slack 웹훅이 없어 경고는 로그와 `job_runs.stats.warnings`에만 남고, 거부가 이어지는 동안 회차마다 난다.
  차단기는 사이트 단위 원인만 센다 — 사이트 전체가 404를 주면(기사 주소 체계 개편) 차단기는 열리지 않고 기사마다 요청 1번씩
  보내며, 건전성 검사 경고로만 드러난다. 건전성 검사는 404도 실패로 세므로, 건강한 언론사의 죽은 URL(재시도 3회 동안 회차 맨
  앞에 온다)이 그 회차에 받은 기사의 절반 이상이면서 동아일보 차단과 겹치면 실행이 실패할 수 있다(차단기 쪽 경로는 막았다).
  새 요청 코드와 RSS 소켓 상한은 테스트 안의 127.0.0.1 소켓 서버(합성 HTML·합성 RSS)와 CI의 PostgreSQL로만 확인했고, 실제
  언론사 페이지에 대고 돌려 보지는 않았다.
