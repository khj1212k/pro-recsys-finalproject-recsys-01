**2026-10-25 결정 — 동아일보는 RSS 요약으로 받는다(범위 종결 C-31, 결정 · 배포 대기).** 결정 주체: 소유자가 "완성 단계까지 멈추지 말고 진행"하라고 위임한 상태에서 내린 결정이다(2026-10-25). 세 안 가운데 하나를 소유자가 따로 승인한 기록은 없다 - 위임에 따른 결정이고 배포 전에 소유자가 뒤집을 수 있다. 결정 9 배포(10-18) 뒤 7일 관측: 동아일보 1,306건 중 본문 ok 99건, `fetch_failed` 673건(전체 언론사의 678건 중), 매 회차 언론사별 차단기가 남은 기사를 미뤘다 - VM 출발지 거절이 그대로다(증거 10). 세 대안(VM에서 받을 수 있는 만큼 / 클라우드 밖에서만 / 피드에서 빼기) 대신 넷째를 고른다: 동아일보 RSS의 요약(10-25에 피드를 다시 받아 확인한 50건 - 길이 84~498자, 중앙값 495자, 기사 앞부분)을 수집 때 본문 칸에 넣고 상태를 `rss_summary`로 닫아 본문 추출 대상에서 뺀다(`Settings.RSS_FEEDS`의 전략 값 `rss_summary`, `crawler/rss_collector.py`). **동아일보 서버에는 본문 요청을 보내지 않는다 - 요약이 없어도 마찬가지다.** 요약 행도 운영 임베딩·클러스터 입력에 들어간다(그 입력에는 상태 필터가 없고, 동아일보가 클러스터에 기여하게 하려는 결정이다). 그래서 수집기가 본문 추출기와 같은 규칙으로 넣는다: 같은 해시(요약 텍스트의 sha256)의 `ok`/`rss_summary` 행이 이미 있거나 같은 묶음 안에서 앞서 나온 요약은 본문 ''에 `duplicate`(분류 뒤 다른 경로로 다시 나온 같은 기사 - 해시는 남긴다), `is_drop_article`이 참인 요약(350자 미만이면 빈 요약 포함, `[포토]` 제목은 200자 미만)은 본문 ''에 `dropped`, 나머지는 `rss_summary`다. 피드별 통계 `summary`(stored·dropped·duplicate)가 `job_runs.stats`에 남는다.

드롭 기준 판단(2026-10-25 측정): 길이와 `[포토]` 규칙은 요약에 그대로 쓴다 - 피드 50건 중 350자 미만은 84자 한 건(2%)이고, 요약이 500자 안팎에서 잘려 350자 미만이면 기사 전문이 짧다는 뜻이라 본문 추출기의 `too_short`와 같은 기사를 가린다. 리스트성 마커 규칙(`실시간`·`랭킹` 등이 들어 있고 700자 미만이면 버림)은 쓰지 않는다: 요약은 길어야 500자라 항상 700자 미만인데, VM `ok` 본문 36,269건에서 앞 500자만 떼어 같은 마커를 찾으면 513건(1.4%, 동아일보 3,022건 중 45건)이 걸린다 - 본문 전체로는 통과한 기사를 요약만 보고 버리게 된다(읽기 전용 집계, 본문은 VM 밖으로 내지 않았다).

DB 변경과 배포 순서: CHECK 제약 `ck_news_raw_extract_status`는 `rss_summary`·`blocked_origin`을 허용하지 않아 코드만 배포하면 동아일보 INSERT가 `CheckViolation`으로 피드째 실패(매시 0건)하고 close SQL도 멈춘다. 새 Alembic 리비전 `b7e4a1c93d52`(down_revision `f1db3221e45f`)가 두 상태를 제약에 더하고, 같은 요약 조회를 받치는 부분 인덱스 `ix_news_raw_content_sha256_rss_summary`(유일하지 않다)를 만든다 - 이 인덱스가 없으면 중복 조회가 `ok`만 덮는 기존 인덱스의 술어를 증명하지 못해 동아일보 피드를 읽을 때마다 `news_raw` 전체를 순차로 읽는다(VM EXPLAIN: Seq Scan, 힙 54 MB·4.3만 행, 해시 50개에 0.18~0.52초, 테이블 크기에 비례해 늘어난다). **Alembic 변경이 있으므로 새 이미지의 첫 ingest 전에 `migrate`를 한다**(런북 6.9). downgrade는 인덱스를 지우고 `blocked_origin`→`fetch_failed`(시도 횟수를 `MAX_EXTRACT_ATTEMPTS` 이상으로 올려 다시 받지 않게), `rss_summary`→`dropped`(본문·임베딩을 비운다 - `ok`로 두면 요약이 본문 행으로 읽혀 동결 반출에 섞인다)다. 배포 전 추출 대기 행은 `scripts/oci/close_donga_pending.sql`로 `blocked_origin`으로 닫는다(도는 ingest가 있으면 멈추고, 보관 표로 되돌릴 수 있다, 런북 6.9).

한계: (1) 요약은 본문의 앞 500자 안팎이라 생성·실험에는 본문과 같지 않다. (2) 동결 반출(실험)은 지금처럼 `ok`만 고르므로 요약 행은 실험에 들어가지 않지만, 운영 임베딩·클러스터 입력에는 들어간다 - 같은 기간의 실험 입력(`ok`만)과 운영 입력(요약 포함)이 다르므로 운영 클러스터의 수치를 실험 결과로 옮기지 않는다. 운영 `cluster_history`에서 기사를 고르는 LLM 평가셋 표본기(`evaluation/llm/evalset.py`)는 상태 필터가 없어 요약이 '본문'으로 섞일 수 있었으므로, 상태 `rss_summary` 기사가 든 클러스터를 후보에서 빼고 수를 보고하게 했다(`articles_body_summary`). Tier 0 → Tier 1 병합 스크립트(`scripts/oci/merge_tier0_news_raw.sql`)는 대상이 `b7e4a1c93d52` 이상이어야 하고, 원본의 `rss_summary` 행이 대상의 `ok`/`rss_summary` 행과 해시가 같으면 `duplicate`로 넣는다. ## 검토한 대안

### 1. 어디서 상시 운영할 것인가
1. **PAYG 전환 후 A1** — A1 용량 우선 배정·유휴 회수 제외가 커뮤니티에서 보고되지만 공식 문서로는 확인하지
   못했다. 결제 수단 등록과 소액 과금 위험. 예산 원칙 위반 → 기각.
2. **A1만 기다린다** — 확보 시점을 알 수 없다(위 재시도 통계). 기다리는 동안 Mac이 단일 장애점으로 남는다 →
   단독으로는 기각, Tier 1로 유지.
3. **Mac만** — MPS 임베딩·LLM 생성·평가에는 가장 빠르지만 24/7이 아니다(증거 6의 4시간 공백) → 개발 계층으로 한정.
4. **E2.1.Micro(1 GB) Tier 0** — 무엇이 들어가는지 실측해서 범위를 정한다 → **채택(수집 데이터 플레인만).**
5. **GitHub Actions 배치 + 외부 DB(리뷰 3.3 B안)** — 무료 러너 조건(공개 저장소), 60일 무커밋 시 cron 비활성,
   러너에서 DB로 가는 터널, 수집 본문이 러너를 거치는 문제. Tier 0 VM이 같은 역할을 더 단순하게 한다 → 보류.
6. **유료 최소 VPS(리뷰 Tier 2)** — 예산 원칙 위반 → 기각(예산 원칙이 바뀌면 재검토).

### 2. Tier 0에서 무엇을 돌릴 것인가
1. 전체 compose(worker 이미지, embed 포함) — worker 이미지에 CPU torch·BGE-M3가 들어 있고 임베딩은 3.6 GB가
   필요하다 → 기각.
2. **수집(rss·extract)·popularity·daily_report만, 전용 슬림 이미지** — 채택. torch·hdbscan·lightgbm·LLM SDK를 뺀
   `docker/ingest.Dockerfile`(의존성은 worker 잠금 파일을 제약으로 걸어 같은 버전)과 `docker/crontab.micro`.
3. 추출 워커 수: 기본 8개(ProdSettings)는 1 GB에서 돌려 보지 않았다. 2개로 빈 DB 첫 ingest(431건)가 추출 132초,
   잡 컨테이너 최대 258 MiB였고(증거 2·3) 매시 신규는 16~60건이라 2개로 충분하다 → 2개로 고정.

### 3. 방화벽
1. **UFW로 22만 허용** — 처음 계획. 그러나 OCI 공식 문서(Compute Best Practices, "Essential Firewall Rules")가
   "Do not use Uncomplicated Firewall (UFW) to edit firewall rules on an Ubuntu image"라고, UFW로 규칙을 고치면
   인스턴스가 부팅되지 않을 수 있다고 경고한다(iSCSI 부트 볼륨용 필수 규칙이 iptables에 있음) → 기각.
   VM에는 `ufw` 패키지가 설치돼 있지 않다(의도).
2. **OCI 이미지 iptables 유지 + IPv6 보강** — 이미지 기본 IPv4 규칙이 이미 "22/tcp 신규 연결만 허용, 나머지
   REJECT"다. 확인만 하고 비어 있던 IPv6 규칙을 같은 정책으로 채운다 → 채택. 목적(인바운드 22만)은 같고,
   실제 상태는 증거 5에 있다.

### 4. 유휴 회수 대응
1. **인위적 CPU 부하**(busy loop·lookbusy류로 p95를 20% 위로) — 효과는 확실하지만 규칙의 취지(쓰지 않는 자원
   회수)를 우회하고, 1/8 OCPU 버스트 자원을 수집 잡과 나눠 쓴다 → 기본 미채택.
2. **회수돼도 잃는 것이 없게 운영 + 조기 경보 + 빠른 재생성** → 채택(결정 6).

### 5. A1로 옮길 때 두 DB를 어떻게 합칠 것인가
1. **Tier 0 DB만 옮긴다** — 11:36 KST 이전 Mac 수집분(690행)과 임베딩 845개를 잃는다 → 기각.
2. **Mac 덤프만 복원한다** — 17:00 KST 이후는 Tier 0에만 있다 → 기각.
3. **Mac 덤프 복원 + Tier 0 행을 URL로 병합** — 두 DB의 `raw_news_id`·`press_id`는 서로 다르므로 id가 아니라
   `raw_news_url`(UNIQUE)로 합치고 언론사는 이름으로 매핑한다. 본문 해시가 이미 있는 행은 `duplicate`로 넣는다
   (부분 UNIQUE `uq_news_raw_content_sha256_ok`) → 채택(결정 4, 런북 6.4).

   언론사 이름 매핑이 빠짐없는지, 결과 행 수가 "병합 전 + 대상에 없는 URL 수"와 같은지 확인하고 아니면 전부
   되돌린다. 같은 URL은 Mac 행(임베딩 있음)을 남기고, 새 URL인데 본문 해시가 기존 ok 행과 같으면 `duplicate`로

   899 + 188 = 1,087행이고, 일회용 DB 리허설 결과가 정확히 이 값이었다(증거 7).

   첫 embed가 채울 임베딩은 약 1.3만 건이 된다 — A1 CPU 임베딩 처리량은 재 본 적이 없다(ADR 0006 한계).

5. **A1 재시도 방식** — 로컬 루프(`.ops/`, gitignore, 기계별 OCID 포함): 1 OCPU/6 GB와 2 OCPU/12 GB를 번갈아

9. **본문 추출: 요청마다 상한, 언론사별 격리, 실행 시간 마감** (2026-10-17, 증거 10 — 코드만, Tier 0 미배포 [2026-10-18 배포 - 상태 "2026-10-18 갱신(배포)"]. 같은 날 검토를
   반영해 RSS 피드별 경고·사이트 단위 원인만 세는 차단기·ingest 시작부터 잰 마감·RSS 소켓 상한·성공 요청 시간 구간을 더했다)
   - 기사 요청은 `crawler/content_extractor/fetch.py`가 보낸다. 연결 10초·소켓 읽기 15초·요청 전체 30초, 라이브러리 안의
     재시도·대기는 없다(리다이렉트만 trafilatura처럼 2번까지 - 우리 코드가 따라가고, 리다이렉트 홉도 같은 30초 안에서 남은 시간만
     받는다. urllib3에 맡기면 홉마다 상한이 새로 시작하고 리다이렉트 응답 본문을 다 읽어 비우므로 요청 1번이 90초를 넘길 수 있다).
     같은 실행 안에서는 2번까지 보낸다(대기 2초, 4xx와 크기 문제는 다시 보내지 않는다). 본문을 읽는 동안에도 읽기마다 소켓
     제한을 남은 시간으로 줄여, 조금씩 흘려보내는 서버도 요청 1번이 30초 안팎에서 끊긴다. 실패하는 기사 1건이 워커를 붙잡는
     시간은 약 4분(증거 10 d)에서 최악 62초(요청 2번 x 30초 + 대기 2초. 소켓 제한이 적용될 때이고 DNS 조회는 상한 밖이다 —
     라이브러리 내부가 바뀌어 연결 객체를 찾지 못하면 요청 1번이 30초 + 읽기 15초까지 갈 수 있다), 빈 응답이면 약 10초로 준다.
     요청 헤더(User-Agent 포함)와 바이트 디코딩은 trafilatura 것을 그대로 쓴다 — 같은 바이트를 받으면 본문 추출에 넘기는
     문자열이 예전과 같다(테스트로 확인). 그래서 성공한 페이지의 본문과 본문 해시는 이 변경으로 바뀌지 않는다. 실패
     원인(`disconnect`·`read_timeout`·`http_403` 등)은 `job_runs.stats`의 `extract.fetch_fail_causes`에, 다운로드에 성공한
     요청의 시간은 `extract.fetch_ok_latency`에 구간(`<5s`·`5-15s`·`>=15s`)별로, 둘 다 언론사별 개수로만 남긴다(URL 없음) —
     예전에는 원인도 시간도 어디에도 남지 않았다.
   - 15초의 근거: VM에서 실패가 없는 회차는 대상 1건에 0.77초(워커 2개, 추출 포함)였고, 성공한 동아일보 기사는 회차 시간을
     1건에 약 3초만 늘렸다(실패 0 회차 136회의 기울기). Mac에서 같은 페이지의 첫 바이트는 0.1~0.3초다. 다만 15초가 느리지만
     결국 성공하던 기사 요청을 끊는지는 **재지 않았다** — 예전 코드는 요청 시간을 남기지 않았고, 같은 서버의 RSS는 VM에서
     성공해도 30~321초·첫 바이트 최대 74초였다(증거 10 c). 그래서 성공한 요청의 시간 구간을 남기고, 배포 뒤 `>=15s` 구간과
     `read_timeout`·`deadline` 비율을 함께 본다 — `ok`가 줄었을 때 차단 때문인지 상한 때문인지 가르는 값이다. RSS에는 같은
     상한을 넣지 않았다(같은 상한이면 그런 느린 성공이 실패로 바뀐다). 대신 요청 전체가 아니라 소켓 대기 1번(연결·읽기
     각각)에 120초 상한(`RSS_SOCKET_TIMEOUT_S`)만 둔다 — 예전에는 feedparser가 urllib을 시간 제한 없이 불러, 붙잡는 RSS
     서버에 ingest가 끝없이 멈출 수 있었다. 대기 1번이 120초를 넘지 않는 느린 성공은 끊지 않는다(대기 1번의 최대값은 재지
     않았다 — 첫 바이트까지가 최대 74초였다).
   - 언론사별 차단기: 한 실행 안에서 같은 언론사 기사가 연달아 3건 **사이트 단위 원인**(연결·읽기 실패, 5xx, 403·408·425·429)으로
     다운로드에 실패하면, 그 언론사의 남은 기사는 이번 실행에서 보내지 않는다(`extract.press_breaker`·`deferred`). 없는 기사
     (404·410 같은 4xx), 크기·리다이렉트 상한, 분류 밖 예외는 그 기사만의 문제라 세지도 0으로 되돌리지도 않는다 — 대상이
     `ORDER BY raw_news_id`라 앞서 실패한 죽은 URL이 언론사마다 회차 맨 앞에 오는데, 그것 3건으로 건강한 언론사의 새 기사를
     미루면 안 된다. 미룬 기사는 DB에 쓰지 않으므로 시도 횟수(상한 3회)를 쓰지 않는다. 예전에는 차단 시간대에 걸린 동아일보
     기사가 회차마다 시도를 하나씩 써서 세 회차 뒤 영구 실패가 됐다(10-16 수집분 280건 중 103건). 거부가 이어지면 회차마다
     가장 오래된 3~4건만 시험 삼아 받으므로, 그런 회차에서 동아일보로 가는 실패 요청은 10번 안팎이다(예전: 7일 약 2만 번 =

       멈춘다(지금 3,351행 모두 0건). 되돌리기 스크립트(이름과 달리 정리용)는 `news_raw`를 바꾸지 않는다: 되돌린 행이 원래 `ok`(본문 있음)이거나 `duplicate`(본문 원래 없음)였고 본문을 복사하지 않아(ADR 0023) 옛 본문이 표로 돌아오지 않는다. 보관한 행이 어떻게 끝났는지
       (미시도·ok·dropped·duplicate·실패·비움)를 알리고 보관 표를 정리한다.
       **다시 받지 못한 행(기사 삭제 등)은 `fetch_failed`로 끝나 본문이 없어진다.** 부푼 본문은 틀린 값이라 보관하지 않는다. **본문 백업의 범위:** 호스트 밖 본문 사본(`full/`)은 수집 27일 이내 행만 담고(`tier0_backup.py`의 `BODY_BACKUP_MAX_AGE_DAYS`) 하루 뒤 지워지므로, 옛 본문을 복원할 수 있는 것은
       재추출 직전에 뜬 백업의 27일 이내 행뿐이다. 수집한 지 27일이 넘은 대상(2026-10-25 13:23 UTC 조회 281행, 오래된 행부터 되돌리므로 첫 배치들)은 어떤 본문 백업에도 없어 다시 받지 못하면 복구할 수 없다 - 부풀지 않은 행이면 본문을 잃는 것이다(보존 기한이 3일 안에 지울 본문).
       **시간 제약:** 보존 기한(30일)으로 대상 행이 하루 45 ~ 210행씩 빠진다(`target=length` + `target=shared`, 13:33 UTC 조회: 10-26 45, 10-27 115, 10-28 156, 10-29 210, 10-30 195, 10-31 188, 11-01 150) - 배포가 늦을수록 되돌릴 행이 준다. 배포 전에는 새 부푼 행이 계속 생긴다
       (추출일 기준 3,000자 이상 비율 10-24 29/95, 10-25 30/159. 목록 글 `ok` 행도 하루 1건쯤 생긴다).

### 6. Mac 정지(12:53~16:50) 동안의 겹침과 공백 — URL 기준 비교

## 결과와 한계
- **비용 $0 유지.** 만든 유료 자원 없음. 셰이프 과금 유형 `ALWAYS_FREE`, 볼륨 합계 150 GB(대기 A1 포함) ≤ 200 GB.
- **1 GB에 수집 데이터 플레인이 들어간다.** 10.5시간 소크에서 MemAvailable 최소 379 MiB(p5 404), 스왑 최대
  105 MiB, OOM 0, 끝난 잡 22/22 성공, 수집 지연 p95 1.5시간. 임베딩·클러스터링·생성은 들어가지 않는다 —
  Tier 0만으로는 뉴스레터를 만들 수 없다.
- **섀도 수집기는 실제로 공백을 메웠다.** Mac이 4시간 멈춘 동안 Mac이 영영 놓친 32건(세계일보)을 Tier 0가 갖고
  있고, 같은 구간 Mac 수집분은 Tier 0가 전부 갖고 있다. 다만 이 수치는 피드 창 크기에 달린 하루치 관측이다.

  정확히 맞았고, 다시 돌려도 바뀌지 않으며(멱등), 검증 실패 시 전부 되돌린다(증거 7).
- **지금 가장 큰 위험: 승격 조건을 통과하지 않은 단독 수집기.** 17:00 KST 이후 수집분은 Tier 0 한 곳에만 있고,
  정상 상태 지표로는 공식 기준상 회수 대상이다(증거 4). 호스트 밖 백업은 수동 `pg_dump` 당겨 오기뿐이며(마지막
  22:18, 795행) 자동화는 보류다 — 회수·디스크 손상 시 마지막 백업 이후를 잃는다. Mac 덤프(899행)도 Mac 디스크에만
  한 부 있다. 이 위험은 노트북 응답성과 맞바꾼 것으로 사용자가 정했다. (2026-10-25: 결정 3의 승격 조건은 증거 13에서 충족했다. 위험의 나머지는 그대로다 -
  유일한 수집기, 공식 유휴 기준상 회수 대상, 사본이 같은 OCI 테넌시 안에 있다.)
- **동아일보 추출이 Tier 0에서 불안정하다.** Mac 899행에는 fetch_failed가 0건인데 Tier 0에서는 10건이 남았고, 그런
  회차는 추출이 20분 넘게 걸렸다. 원인(OCI IP 제한 여부)은 두 수집기를 같은 시간에 돌려 비교해야 가를 수 있다.

  5.0~8.9시간). 호스팅과 무관한 수집기 결함이지만 수집 지연 지표와 시점 기준(point-in-time) 평가셋의 기사 시각에

### 2026-10-06 갱신 (증거 8)
- **1 GB VM이 10일을 버텼다.** 14,230행을 모았고 OOM 0, 유휴 회수 없음, 예약 재부팅 뒤 사람 손 없이 다음 정시
  회차부터 수집을 이어 갔다. 비용은 여전히 $0다(만든 자원은 E2.1.Micro 1대와 부트 볼륨 50 GB뿐).
- **수집 품질은 09-26 하루치보다 나빠졌다.** 정시 회차의 85.0%만 성공했고(233회 중 198회), ingest가 1시간을
  넘겨 다음 회차를 건너뛴 것이 27회다. 실패 8건과 fetch_failed의 99%가 동아일보 쪽이다. "매시 수집"이라고 쓰려면

### 2026-10-17 갱신 2 (증거 10, 결정 9)
- **동아일보 실패 원인을 갈랐다.** 동아일보 서버가 VM에서 온 요청을 연결 단계에서 거부한다 — 같은 시각 같은 URL·User-Agent로
  Mac은 20/20 성공, VM은 0/20. HTTP 오류·페이지 개편·리다이렉트는 아니다. VM의 IP 하나인지, OCI 대역·일본 출발 전체인지는
  모른다.
- **1시간을 넘기는 회차의 대부분은 우리 쪽 재시도 구조 탓이었다.** 실패 기사 1건이 HTTP 요청 9번과 대기 93초가 돼 워커를
  약 4분 붙잡았고, 추출 시간은 실패 수로 R² 0.96만큼 설명된다. 결정 9로 고쳤지만 **배포하지 않았다** — "1시간 초과 회차가
  없어진다"는 아직 계산(RSS 단계가 :50 전에 끝나면 :51 무렵 종료)이지 측정이 아니다.
- **이 수정으로 동아일보 수집량이 돌아오지는 않고, 줄 수도 있다.** 거부되는 동안은 받을 수 없다. 늘 수 있는 것은 미룬 기사가
  시도를 쓰지 않아 거부가 풀린 뒤에 받을 수 있게 되는 몫이다. 줄 수 있는 쪽도 있다: 기사 1건에 보내는 요청이 9번에서 2번으로
  줄고(그 2번이 읽기 15초·요청 30초 상한에 걸리는 느린 성공도 있을 수 있다 — 재지 않았다), 차단기가 회차당 동아일보 처리량을
  묶는다 — 예전 순서에 대 보면 회차당 9.4건으로 새 기사 유입(약 8.8건)과 비슷하다(증거 10 f). 어느 쪽이 큰지는 배포 뒤에 잰다.

  추출 경고를 나눠서), `extract.fetch_fail_causes`의 원인 구성, `extract.fetch_ok_latency`의 `>=15s` 구간과 `read_timeout`·
  `deadline` 비율(함께 늘면 상한이 느린 성공을 끊고 있을 수 있다 — 차단의 `disconnect`·0바이트와 가른다). 확인 쿼리는 런북 6.6.
- **남은 한계:** RSS 단계 전체에는 시간 상한이 없다 — 소켓 대기 1번 120초만 있고, 추출 마감을 ingest 시작부터 재서 RSS가 늦은
  만큼 추출이 줄 뿐이다. 피드 여러 개가 한꺼번에 붙잡히거나 조금씩 흘려보내는 RSS 서버가 있으면 다음 정시 회차와 겹칠 수 있다
  (관측된 적 없음, 결정 9). 동아일보 RSS 실패(418회 중 263회, 10-17 06:11 UTC 기준 423회 중 267회)는 그대로이고, 이제 피드별
  경고로 보인다. VM에 Slack 웹훅이 없어 경고는 로그와 `job_runs.stats.warnings`에만 남고, 거부가 이어지는 동안 회차마다 난다.
  차단기는 사이트 단위 원인만 센다 — 사이트 전체가 404를 주면(기사 주소 체계 개편) 차단기는 열리지 않고 기사마다 요청 1번씩
  보내며, 건전성 검사 경고로만 드러난다. 건전성 검사는 404도 실패로 세므로, 건강한 언론사의 죽은 URL(재시도 3회 동안 회차 맨
  앞에 온다)이 그 회차에 받은 기사의 절반 이상이면서 동아일보 차단과 겹치면 실행이 실패할 수 있다(차단기 쪽 경로는 막았다).

### 2026-10-25 갱신 2 (RSS 재시도·새 상태 집계, 결정 9)

**Tier 0에는 배포하지 않았다** - Tier 0는 이 시각 동아일보 요약 전환 코드(PR #59 병합 `03b174c`)로 돈다(Alembic `b7e4a1c93d52`, `job_runs.git_sha`는 04:35 UTC popularity부터 `03b174c`이고 그 앞 04:05 UTC ingest까지는 재배포 전의 `2b74c25`(Merge #58)였다). 아래 효과는 계산이고 측정이 아니다.

**새 상태 집계** (동아일보가 '본문 0'으로 실패처럼 보이지 않게)
- `daily_report`의 신규 기사 집계에 `rss_summary`(요약)와 `blocked_origin`(출발지 거절)을 더했다. 총합 줄은 "본문 N, 요약 N, … 출발지 거절 N", 언론사 줄은 그 둘이 있는 언론사에만 적는다
  (동아일보: `본문 0, 요약 186, 출발지 거절 4, 임베딩 186`; 없는 언론사의 줄은 그대로). 예전 모양의 리포트(키 없음)는 예전 문구 그대로 그린다.
- **오경보 하나를 함께 막았다**: '같은 본문 반복' 판단(`daily_report.same_body_suspects`)의 분모(본문을 받은 기사)에 `rss_summary`가 없으면, 요약이 대부분인 동아일보는 하루 요약 190건에 짧은 요약(`dropped`) 3건과
  같은 요약(`duplicate`) 3건만 있어도 6건 중 3건(50%)으로 걸린다. 분모에 `rss_summary`를 넣었다. 요약 피드가 한 가지 요약만 내보내는 고장(첫 건만 `rss_summary`, 나머지 `duplicate`)은 그대로 걸린다.
  ingest의 회차별 같은 검사는 본문 추출기의 통계만 보므로 요약 행이 들어오지 않아 바꾸지 않았다.
- ingest의 `news_raw_snapshot`(job_runs.stats.news_raw)은 `with_content`를 'ok' 본문 그대로 두고 `with_summary`(지금 요약이 본문 칸에 있는 `rss_summary` 행)를 따로 센다. **합치지 않은 이유**: 요약은 약 500자라 본문이 아니고,
  동결 반출·평가는 `ok`만 쓰며 임베딩·클러스터는 둘 다 쓴다("2026-10-25 결정 — 동아일보"의 한계 2) - 합친 수에서는 어느 쪽이 얼마인지 되돌릴 수 없지만, 합쳐서 보려면 두 값을 더하면 된다. 보존 기한으로 비운 행은 상태와 상관없이 `body_purged`다(예전과 같다).
- `pipeline/stages.py`의 임베딩 단계 통계 분류는 **이미 고쳐져 있다**(8723bd7): `blocked_origin`은 `no_content`, 본문을 비운 `ok`/`rss_summary`는 `body_purged`이고 `tests/test_embed_stage_status_counts.py`가 확인한다. 이 변경에서 손대지 않았다.

  일부만 비는 경우(예: 절반이 `dropped`)는 이 규칙이 보지 못하고 `daily_report`의 언론사 줄(요약 N)과 `per_feed` 통계로 본다. **`check_extract_health`에는 넣지 않았다**: 그 함수가 받는 것은 본문 추출기의 통계이고 요약 행은 추출기를 거치지 않으므로
  동아일보는 거기에 나오지 않는다(그래서 '본문 0'이 추출 실패로 세어지지도 않는다). 또 그 함수는 잡을 실패시킬 수 있어 읽기 단계의 통계를 섞을 곳이 아니다.

**`rss_retry`** (`jobs/tasks/rss_retry.py`, `docker/crontab.micro`의 `40 * * * *`, 런북 4.2)
- 직전 ingest 실행(RSS 통계가 있는 가장 최근 `job_runs`)의 `stats.rss.per_feed`에서 `error`가 있던 피드 - 설정에 아직 있는 것 - 만 `collect_rss(feeds=...)`로 다시 읽는다. 같은 호스트 건너뛰기 규칙은 읽는 피드끼리 그대로 적용된다
  (국민일보 여섯 피드가 모두 실패했으면 첫 피드만 시도한다). `collect_rss`의 기존 호출(`hours`만)은 바뀌지 않는다. `press_id not found`는 요청 전의 설정 문제라 다시 읽지 않는다.
- 본문 추출은 하지 않는다: 'direct' 피드의 새 기사는 다음 정시 ingest(:05)가 추출하고, 요약 피드는 수집 때 본문 칸이 채워진다. 실패한 피드가 없으면 요청 없이 끝난다(`succeeded`, `retry_feeds` 빈 목록).
- **ingest와 겹치지 않는다 - 락을 공유한다**: ingest의 advisory lock을 따로 잡고 읽는다. ingest가 돌고 있으면 `skipped`(`ingest_running`)다. 요약 행의 중복 방지는 DB가 아니라 수집기가 맡으므로(그 결정의 한계 3) 수집이 겹치면 같은 요약이 두 행이 될 수 있다.
  락을 검사만 하고 놓으면 검사 뒤에 :05 ingest가 시작해 겹칠 수 있어, 읽는 동안 쥐는 방식을 골랐다. 대가: 이 잡이 :05를 넘기면 그 회차의 ingest가 `lock_held`로 건너뛰어진다. 이 잡은 RSS 단계의 일부이고 10-16 ~ 10-25 ingest 211회의 RSS 단계 전체가
  중앙값 22초·최대 136초였으므로 :40에 시작해 :05를 넘길 일은 없다고 본다. 단 읽기 1번 안의 총시간 상한은 없다(결정 9의 남은 한계와 같다) - 느린 서버가 소켓 대기를 120초 안으로 이어 가면 길어질 수 있고, 관측된 적은 없다.
  runtime의 잡 이름 락(`rss_retry`)은 이 잡끼리의 겹침을 막는다. 시간 예산 같은 별도 장치는 두지 않았다.
- 같은 ingest 실행의 실패 피드는 **한 번만** 다시 읽는다(`stats.source_run_id`) - ingest가 건너뛰어져 새 실행이 없는 시간에 같은 목록을 되풀이하지 않는다. 그래서 피드 하나의 시간당 읽기는 최대 2회(ingest :05 + :40)다.
  관측한 동아일보 실패 158회는 모두 예외(`RemoteDisconnected` 157·`TimeoutError` 1)였고 `feed unreadable`(bozo) 형태는 0회였다. 이 예외는 feedparser가 잡지 않고 올려 `parse_feed_with_retry`가 다시 보내지 않으므로(응답 도중의 시간 초과와 같다 - `_fetch_feed` 주석)
  실패한 읽기는 요청 1번이다. 그래서 이 형태가 이어지면 동아일보 서버로 가는 요청은 하루 약 18번(실패한 읽기 18회 x 1번)이 늘 뿐이다. 하루 최대 약 54번(18회 x `MAX_FETCH_RETRIES` 3번)은 연결 단계에서 막혀 bozo로 돌아오는 형태일 때의 상한이고, 관측하지 못했다. 다른 피드는 같은 기간 ingest 211회 중 2회(국민일보)만 실패해 사실상 늘지 않는다.
  차단을 피하는 변경이 아니다 - User-Agent·프록시·다른 주소는 쓰지 않는다(범위 종결 C-31).
- 재시도가 또 실패해도 잡은 성공이고 경고를 더하지 않는다(그 회차의 ingest가 이미 피드별 경고를 냈다 - 더하면 알림이 매시 두 배가 된다). 결과는 `stats.recovered`·`stats.still_failed`와, ingest와 같은 자리·모양의 `stats.rss.per_feed`에 남는다.
  `source_run_id`는 읽기 전에 중간 기록(checkpoint)으로 남겨, 읽는 도중 죽어도 같은 실행을 다시 읽지 않는다.
- `docker/crontab`(Mac·Tier 1)에는 넣지 않았다 - Tier 1이 같은 출발지 거절을 받는지는 모르고, 확보되면 그때 정한다.
