# ADR 0026: 호스팅 계층과 비상 계획 — Always Free만으로 (개발 Mac · Tier 0 E2.1.Micro · Tier 1 A1)

## 상태
채택됨 (2026-09-26). 같은 날 17:00 KST에 전제가 바뀌어 결정 2를 갱신했다 — 사용자 요청으로 Mac 수집 스택을
내렸고, A1이 확보될 때까지 **Tier 0가 유일한 수집기**다(승격 조건 3을 통과하지 않은 상태에서의 결정이며, 위험은
결과와 한계에 적었다). Tier 1(A1)은 용량 부족으로 아직 확보하지 못했다 — 확보되면 결정 4의 측정 결과로 이 ADR을
갱신한다. 증거는 같은 날 22:18 KST까지의 관측으로 갱신했다. 운영 절차는 [runbook-hosting.md](../runbook-hosting.md).

## 컨텍스트
- **예산: 호스팅 비용 $0.** 유료 전환(PAYG 포함)은 하지 않는다(사용자 결정). LLM API 비용은 이 ADR 범위 밖이다.
- **기존 운영:** Mac(Apple M2 16 GB, colima) 위의 compose 스택이 매시 수집하고(기록 시스템), BGE-M3 임베딩은
  호스트 MPS(launchd)로 돌았다(ADR 0006). 노트북은 잠자기·재부팅·이동 때문에 수개월 상시 운영이 불가능하고,
  평가셋에 필요한 5~7일 연속 수집의 단일 장애점이다(2026-09-26 아키텍처 리뷰 D2). 실제로 2026-09-26
  12:53~16:50 KST에 colima VM이 멈춰 Mac 수집이 4시간 끊겼다(증거 6).
- **2026-09-26 17:00 KST, Mac 스택 중단:** 노트북 응답성을 지키려고 사용자가 로컬 서버를 모두 내리게 했다(colima·
  compose·launchd 임베더). 직전 상태는 `pg_dump -Fc` 덤프(16:59 KST, `news_raw` 899행)로 저장소 밖에 보관했다.
- **OCI 테넌시(2026-09-26 CLI 확인):** 홈 리전 ap-tokyo-1, 가용 도메인 1개. 구독 `plan-type=FREE_TIER`,
  `upgrade-state=PROMO`(체험 기간), `is-intent-to-pay=false` — PAYG가 아니다.
- **A1은 확보되지 않는다:** 2026-09-26 00:40~22:18 KST에 A1.Flex 생성 791회 시도 — "Out of host capacity" 418회,
  "Too many requests"(429) 373회, 성공 0회, 한도 초과(LimitExceeded) 0회. 요청 자체는 한도 안이고 용량만 없다.
  재시도 루프는 Mac에서 돌기 때문에 Mac이 멈춘 12:52~16:43 KST에는 시도가 없었다. 루프는 계속 돈다.
- **공식 Always Free 조건**(docs.oracle.com "Always Free Resources", 2026-09-26 조회):
  E2.1.Micro는 테넌시당 2대, 1/8 OCPU(추가 CPU를 쓸 수 있음), 메모리 1 GB, 인터넷 50 Mbps.
  A1은 월 1,500 OCPU-시간·9,000 GB-시간(상시 2 OCPU/12 GB 상당). 부트+블록 볼륨 합계 200 GB.
  Always Free 컴퓨트는 홈 리전에서만 만들 수 있고, "out of host capacity"는 일시적인 셰이프 부족이다.
- **유휴 회수 규칙**(같은 문서): "Idle Always Free compute instances may be reclaimed by Oracle."
  7일 동안 다음이 **모두** 참이면 유휴로 본다 — CPU 사용률 95번째 백분위 < 20%, 네트워크 사용률 < 20%,
  메모리 사용률 < 20%(A1 셰이프만). 집계 해상도, 네트워크 사용률의 분모, 회수가 정지인지 삭제인지,
  사전 통지 여부는 문서에 없다.
- **임베딩 메모리:** BGE-M3 fp32 로드에만 익명 메모리 3.6 GB가 필요하다(ADR 0006 증거 5). 1 GB 호스트에서는
  임베딩을 돌릴 수 없다.

## 검토한 대안

### 1. 어디서 상시 운영할 것인가
1. **PAYG 전환 후 A1** — A1 용량 우선 배정·유휴 회수 제외가 커뮤니티에서 보고되지만 공식 문서로는 확인하지
   못했다. 결제 수단 등록과 소액 과금 위험. 예산 원칙 위반 → 기각.
2. **A1만 기다린다** — 확보 시점을 알 수 없다(위 재시도 통계). 기다리는 동안 Mac이 단일 장애점으로 남는다 →
   단독으로는 기각, Tier 1로 유지.
3. **Mac만** — MPS 임베딩·LLM 생성·평가에는 가장 빠르지만 24/7이 아니다(증거 6의 4시간 공백) → 개발 계층으로 한정.
4. **E2.1.Micro(1 GB) Tier 0** — 무엇이 들어가는지 실측해서 범위를 정한다 → **채택(수집 데이터 플레인만).**
5. **GitHub Actions 배치 + 외부 DB(리뷰 3.3 B안)** — 무료 러너 조건(공개 저장소), 60일 무커밋 시 cron 비활성,
   러너에서 DB로 가는 터널, 수집 본문이 러너를 거치는 문제. Tier 0 VM이 같은 역할을 더 단순하게 한다 → 보류.
6. **유료 최소 VPS(리뷰 Tier 2)** — 예산 원칙 위반 → 기각(예산 원칙이 바뀌면 재검토).

### 2. Tier 0에서 무엇을 돌릴 것인가
1. 전체 compose(worker 이미지, embed 포함) — worker 이미지에 CPU torch·BGE-M3가 들어 있고 임베딩은 3.6 GB가
   필요하다 → 기각.
2. **수집(rss·extract)·popularity·daily_report만, 전용 슬림 이미지** — 채택. torch·hdbscan·lightgbm·LLM SDK를 뺀
   `docker/ingest.Dockerfile`(의존성은 worker 잠금 파일을 제약으로 걸어 같은 버전)과 `docker/crontab.micro`.
3. 추출 워커 수: 기본 8개(ProdSettings)는 1 GB에서 돌려 보지 않았다. 2개로 빈 DB 첫 ingest(431건)가 추출 132초,
   잡 컨테이너 최대 258 MiB였고(증거 2·3) 매시 신규는 16~60건이라 2개로 충분하다 → 2개로 고정.

### 3. 방화벽
1. **UFW로 22만 허용** — 처음 계획. 그러나 OCI 공식 문서(Compute Best Practices, "Essential Firewall Rules")가
   "Do not use Uncomplicated Firewall (UFW) to edit firewall rules on an Ubuntu image"라고, UFW로 규칙을 고치면
   인스턴스가 부팅되지 않을 수 있다고 경고한다(iSCSI 부트 볼륨용 필수 규칙이 iptables에 있음) → 기각.
   VM에는 `ufw` 패키지가 설치돼 있지 않다(의도).
2. **OCI 이미지 iptables 유지 + IPv6 보강** — 이미지 기본 IPv4 규칙이 이미 "22/tcp 신규 연결만 허용, 나머지
   REJECT"다. 확인만 하고 비어 있던 IPv6 규칙을 같은 정책으로 채운다 → 채택. 목적(인바운드 22만)은 같고,
   실제 상태는 증거 5에 있다.

### 4. 유휴 회수 대응
1. **인위적 CPU 부하**(busy loop·lookbusy류로 p95를 20% 위로) — 효과는 확실하지만 규칙의 취지(쓰지 않는 자원
   회수)를 우회하고, 1/8 OCPU 버스트 자원을 수집 잡과 나눠 쓴다 → 기본 미채택.
2. **회수돼도 잃는 것이 없게 운영 + 조기 경보 + 빠른 재생성** → 채택(결정 6).

### 5. A1로 옮길 때 두 DB를 어떻게 합칠 것인가
1. **Tier 0 DB만 옮긴다** — 11:36 KST 이전 Mac 수집분(690행)과 임베딩 845개를 잃는다 → 기각.
2. **Mac 덤프만 복원한다** — 17:00 KST 이후는 Tier 0에만 있다 → 기각.
3. **Mac 덤프 복원 + Tier 0 행을 URL로 병합** — 두 DB의 `raw_news_id`·`press_id`는 서로 다르므로 id가 아니라
   `raw_news_url`(UNIQUE)로 합치고 언론사는 이름으로 매핑한다. 본문 해시가 이미 있는 행은 `duplicate`로 넣는다
   (부분 UNIQUE `uq_news_raw_content_sha256_ok`) → 채택(결정 4, 런북 6.4).

## 결정
1. **계층과 배치** (2026-09-26 17:00 KST 이후)

   | 작업 | 개발(Mac) | Tier 0 (E2.1.Micro) | Tier 1 (A1) |
   |---|---|---|---|
   | Postgres + pgvector | 꺼 둠 — 16:59 KST 덤프만 보관 | O — **유일한 수집 DB** | O — 확보 시 기록 시스템 |
   | 매시 `ingest --stages rss,extract` | 꺼 둠 | O (추출 워커 2개) | O |
   | `embed`(BGE-M3) | 필요할 때 수동(MPS) | X | O (컨테이너 CPU) |
   | `cluster`(HDBSCAN) | 필요할 때 수동 | X | O |
   | `popularity`, `daily_report` | 꺼 둠 | O | O |
   | `generate`(LLM API) | 수동·평가 시 | X | 비용 가드 결정 후 |
   | API(FastAPI) | 필요할 때 루프백 | X (`--profile api`로만) | O (루프백 + 리버스 프록시) |
   | 반출 금지 데이터(EB-NeRD 등) | O (Mac 전용) | X | X |

2. **기록 시스템(갱신)** — 11:36 KST까지는 Mac, 11:36~17:00 KST는 두 곳에 겹쳐 있고, 17:00 KST 이후는 Tier 0에만
   있다. 즉 지금의 기록 시스템은 "Mac 덤프(동결, 899행) + Tier 0 DB"의 합집합이다. Tier 0는 승격 조건(결정 3)을
   통과하지 않은 채 유일한 수집기가 됐으므로 "운영 중"이 아니라 **"임시 단독 수집"**이라고 부른다.
   이 기간 Tier 0 DB의 호스트 밖 백업은 Mac이 SSH로 당겨 오는 `pg_dump -Fc`(런북 6.5)이고, 자동화는
   Mac에서 상주 작업을 돌리지 않기로 한 동안 보류다 — 백업 간격만큼이 회수·장애 시 최대 손실이다.
3. **Tier 0를 기록 시스템으로 올리는 조건** — 모두 만족 전에는 "배포됨/운영 중"이라 쓰지 않는다:
   (a) 7일 소크에서 잡 성공률 ≥ 95%, OOM 0, 수집 지연 p95 ≤ 3시간 (b) 매일 호스트 밖 백업과 복원 검증 1회
   (c) Mac→Tier 0 전환 절차를 일회용 DB에서 검증. 2026-09-26 22:18 KST 현재: (a) 약 10.5시간 경과, 끝난 잡
   21/21 성공·OOM 0, 수집 지연 p95 1.5시간(증거 3) (b) 호스트 밖 백업 1회(22:18 수동 당겨 오기, 목록·행 수만 확인),
   매일·복원 검증은 미충족 (c) Mac이 내려가 원래 뜻의 전환은 사라졌고, 그 자리를 대신하는 "Mac 덤프 + Tier 0 병합"
   절차를 일회용 DB에서 검증했다(증거 7).
4. **Tier 1(A1) 승격과 데이터 이전** — 확보되면 같은 초기 설정 스크립트 + 기본 compose(전체 worker 이미지, arm64
   직접 빌드). 데이터는 대안 5.3: A1에 Mac 덤프를 `pg_restore`하고, 스케줄러를 멈춘 채 Tier 0 `news_raw`를
   `scripts/oci/merge_tier0_news_raw.sql`로 URL 기준 병합한다(런북 6.4). 스크립트는 단일 트랜잭션 안에서
   언론사 이름 매핑이 빠짐없는지, 결과 행 수가 "병합 전 + 대상에 없는 URL 수"와 같은지 확인하고 아니면 전부
   되돌린다. 같은 URL은 Mac 행(임베딩 있음)을 남기고, 새 URL인데 본문 해시가 기존 ok 행과 같으면 `duplicate`로
   넣는다. 병합된 Tier 0 행은 임베딩이 없으므로 A1의 embed 잡이 채운다. 22:17 KST 기준 기대값은
   899 + 188 = 1,087행이고, 일회용 DB 리허설 결과가 정확히 이 값이었다(증거 7).
   이전이 끝날 때까지 Tier 0 수집은 멈추지 않는다 — 병합 직전에 Tier 0 CSV를 새로 뽑고, A1 스케줄러를 켠 뒤
   Tier 0를 한 번 더 병합해(멱등) 그 사이 수집분까지 옮긴다. 7일 소크를 통과하면 A1을 기록 시스템으로 선언하고
   Tier 0는 섀도로 되돌리거나 내린다. 블록 볼륨 합계는 A1 100 GB + Micro 50 GB = 150 GB로 200 GB 안이다.
5. **A1 재시도 방식** — 로컬 루프(`.ops/`, gitignore, 기계별 OCID 포함): 1 OCPU/6 GB와 2 OCPU/12 GB를 번갈아
   한 번씩 요청, 30초 간격, 429(Too many requests)면 대기를 2배로(최대 600초), 같은 이름의 인스턴스가 생기면
   멈춘다. Micro는 몇 분 동안 몇 번만 재시도한다(Micro는 첫 시도에 생성됐다).
6. **유휴 회수 대응** — 회수가 "삭제"일 수도 있다고 가정한다.
   - 실측상 Tier 0는 수집만 도는 정상 상태에서 **CPU p95 9.2%, 네트워크 p95 0.08%**(약 10시간)로, 7일간 이대로면
     공식 기준상 유휴에 해당한다(증거 4). 즉 회수 가능성은 이론이 아니라 기본값이다.
   - 그래서 손실 한도를 백업 간격으로 묶는다(결정 2). Tier 0가 섀도였던 동안은 회수돼도 손실이 없었지만,
     17:00 KST 이후에는 마지막 호스트 밖 백업 이후 수집분을 잃는다. 기준 기간이 7일이라 생성(09-26) 뒤 7일이
     차는 10-03 전에는 기준을 채울 관측 기간이 없다고 본다(추론 — 문서가 창의 시작 시점을 밝히지 않는다).
     그때까지 A1이 없으면 이 결정을 다시 본다(아래).
   - `scripts/oci/idle_check.py`: oci_computeagent 1분 지표로 공식 기준을 근사 계산(CPU·메모리 p95, 네트워크는
     분당 max(수신, 송신)/셰이프 대역폭의 p95)해 기준+5%p 안쪽이면 종료 코드 2, 기준상 유휴면 3.
   - 재생성 절차를 스크립트화해 실측 약 10분(증거 5)으로 줄였다.
   - A1에서는 메모리 기준이 적용되므로, BGE-M3를 상주시키는 임베딩 서비스(12 GB의 20% = 2.4 GB 이상)가
     "모두 참" 조건을 깬다 — A1 확보 후 `MemoryUtilization` 실측으로 확인한다.
   - 인위적 CPU 부하는 쓰지 않는다. A1 확보가 늦어져 Tier 0 단독 수집이 7일을 넘기는데 백업 자동화도 없다면
     이 결정을 다시 본다(ADR 갱신).
7. **호스트 기본값** — `scripts/oci/micro_bootstrap.sh`: 2 GB 스왑(`swappiness=10`), 보안 업데이트 자동 적용(재부팅
   필요 시 03:40 KST), fail2ban, Ubuntu 아카이브 Docker(로그 상한·live-restore), rpcbind·ModemManager·udisks2 정지,
   sshd(root·비밀번호 로그인 금지, `AllowUsers`), 방화벽은 대안 3.2. DB·API 포트는 루프백에만 publish한다
   (Docker publish는 iptables INPUT을 우회하므로).
8. **기계별 값(IP·OCID·SSH 설정·known_hosts)은 저장소 밖**(메인 체크아웃 `.ops/micro/`, gitignore)에 둔다.

## 증거
측정 환경: OCI ap-tokyo-1, VM.Standard.E2.1.Micro(AMD EPYC 7551, vCPU 2개 표시, MemTotal 952~954 MiB),
Canonical-Ubuntu-24.04-2026.09.18-0(부팅 후 24.04.5, 커널 7.0.0-1011-oracle), Docker 29.1.3,
Compose 2.40.3, PostgreSQL 16.15(pgvector 이미지), 부트 볼륨 50 GB(VPU 10). OCI CLI 3.94.0.
모든 시각은 2026-09-26 KST(괄호 안 UTC는 원자료 표기).

### 1. $0 확인 (생성 전, CLI)
| 항목 | 값 |
|---|---|
| 홈 리전 | ap-tokyo-1 (`is-home-region=True`) |

## 결과와 한계
- **비용 $0 유지.** 만든 유료 자원 없음. 셰이프 과금 유형 `ALWAYS_FREE`, 볼륨 합계 150 GB(대기 A1 포함) ≤ 200 GB.
- **1 GB에 수집 데이터 플레인이 들어간다.** 10.5시간 소크에서 MemAvailable 최소 379 MiB(p5 404), 스왑 최대
  105 MiB, OOM 0, 끝난 잡 21/21 성공, 수집 지연 p95 1.5시간. 임베딩·클러스터링·생성은 들어가지 않는다 —
  Tier 0만으로는 뉴스레터를 만들 수 없다.
- **섀도 수집기는 실제로 공백을 메웠다.** Mac이 4시간 멈춘 동안 Mac이 영영 놓친 32건(세계일보)을 Tier 0가 갖고
  있고, 같은 구간 Mac 수집분은 Tier 0가 전부 갖고 있다. 다만 이 수치는 피드 창 크기에 달린 하루치 관측이다.
- **A1 이전 데이터 경로는 리허설을 마쳤다.** Mac 덤프 복원 + Tier 0 URL 병합이 실데이터로 기대 행 수(1,087)와
  정확히 맞았고, 다시 돌려도 바뀌지 않으며(멱등), 검증 실패 시 전부 되돌린다(증거 7).
- **지금 가장 큰 위험: 승격 조건을 통과하지 않은 단독 수집기.** 17:00 KST 이후 수집분은 Tier 0 한 곳에만 있고,
  정상 상태 지표로는 공식 기준상 회수 대상이다(증거 4). 호스트 밖 백업은 수동 `pg_dump` 당겨 오기뿐이며(마지막
  22:18, 795행) 자동화는 보류다 — 회수·디스크 손상 시 마지막 백업 이후를 잃는다. Mac 덤프(899행)도 Mac 디스크에만
  한 부 있다. 이 위험은 노트북 응답성과 맞바꾼 것으로 사용자가 정했다.
- **동아일보 추출이 Tier 0에서 불안정하다.** Mac 899행에는 fetch_failed가 0건인데 Tier 0에서는 10건이 남았고, 그런

- **AI타임스 발행 시각이 수집 시각보다 5~9시간 뒤로 저장된다**(증거 3 — Tier 0 6.2~9.0시간, Mac 덤프
  5.0~8.9시간). 호스팅과 무관한 수집기 결함이지만 수집 지연 지표와 시점 기준(point-in-time) 평가셋의 기사 시각에
